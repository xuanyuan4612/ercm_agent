## 一、核心问题：Hermes Agent 是 ReAct、Plan 还是其他架构？

### 1.1 短期回答

**都不是。** Hermes 采用的是 **"确定性 Pipeline + Stage Agent + HITL 守门"** 架构，不属于 AI Agent 社区常见的 ReAct、Plan-and-Execute、Supervisor-Worker 或完全自主型 Agent 中的任何一种。它是为**企业风控的高合规、高后果场景**专门设计的混合架构。

### 1.2 一句话定位

> **Module Graph（确定性状态机）是主控，Stage Agent 是单阶段结构化顾问，HITL（Human-in-the-Loop）是每道门的守门员，三者组合形成"确定性流程编排 + AI 增强分析 + 人类最终裁决"的三层架构。**

## 二、与主流 Agent 架构模式的逐项对比

### 2.1 ReAct (Reasoning + Acting) 模式

ReAct 模式的核心特征是：Agent 在**思考→行动→观察→思考**的循环中自主决定下一步做什么。

```
典型 ReAct 循环:
  Thought: 我需要查一下这个供应商的历史交易记录
  Action: sql_query("SELECT * FROM transactions WHERE supplier='XX科技'")
  Observation: 返回 200 条记录...
  Thought: 发现异常交易集中在 2024 Q3，需要进一步分析采购员关联关系
  Action: search_personnel("张某")
  Observation: 张某是这些订单的采购员...
  Thought: 证据链完整，可以下结论了
  Final Answer: 张某涉嫌利益输送...
```

| 维度 | ReAct 模式 | Hermes 架构 | 分析 |
|------|-----------|-------------|------|
| **决策权** | Agent 自主决定调用什么工具、调用多少次 | Module Graph 确定性路由，Agent 只能在当前阶段内按预设工具集调用 | ❌ 完全不同 |
| **循环性** | Agent 在思考-行动-观察中循环，直到得出最终答案 | Agent 执行一次推理 → 输出结构化结果 → 进入 HITL 等待，不循环 | ❌ 完全不同 |
| **工具调用** | Agent 自主决定调用时机和参数 | 工具调用依赖图是预定义的（并行 3-4 路检索），Agent 不选择是否调用 | ❌ 完全不同 |
| **状态跳转** | Agent 自行决定任务完成并停止 | 状态跳转由 LangGraph 条件边决定，Agent 不感知也不控制 | ❌ 完全不同 |
| **可审计性** | 思考链可记录，但决策是 AI 自主做出的 | 每步决策都有确定性规则 + 人工守门记录 | ❌ 完全不同 |

**结论：Hermes 不是 ReAct 架构。** ReAct 的自由循环与 Hermes 的确定性流程控制在根本上互斥。

### 2.2 Plan-and-Execute 模式

Plan-and-Execute 模式的核心特征是：Agent 先生成完整计划，再逐步执行，执行过程中可以根据结果调整计划。

```
典型 Plan-and-Execute:
  Plan: 1) 检索组织架构 → 2) 查询供应商信息 → 3) 分析交易记录 → 4) 撰写结论
  Execute Step 1: 检索组织架构 ✓
  Execute Step 2: 查询供应商信息 ✓ (发现新线索)
  Re-plan: 在 Step 3 之前，先补充调查关联人员...
  Execute Step 2.5: 查询关联人员 ✓
  Execute Step 3: 分析交易记录 ✓
  Execute Step 4: 撰写结论 ✓
```

| 维度 | Plan-and-Execute 模式 | Hermes 架构 | 分析 |
|------|----------------------|-------------|------|
| **计划制定** | Agent 自主规划执行步骤 | 调查方案 Agent (`investigation-agent`) 生成方案，但方案是交付给人类执行的文档，不是 Agent 自身的执行计划 | 🔸 表面相似但本质不同 |
| **动态重规划** | Agent 根据执行结果自行调整计划 | 不存在 Agent 级别的动态重规划；如果需要补充调查，必须通过确定性回退循环 + HITL | 🔸 有回退但非 Agent 自主 |
| **执行者** | Agent 自己执行计划中的每个步骤 | Agent 不执行计划，它只生成方案文档供碳基执行 | ❌ 完全不同 |
| **主控权** | Agent 拥有执行和调整的主控权 | Module Graph 和碳基拥有主控权 | ❌ 完全不同 |

| 维度 | Plan-and-Execute 模式 | Hermes 架构 |
|------|----------------------|-------------|
| **计划制定** | Agent 自主规划执行步骤 | 调查方案 Agent (`investigation-agent`) 生成方案，但方案是交付给人类执行的文档，不是 Agent 自身的执行计划 |
| **计划制定** | Agent 自主规划执行步骤 | 调查方案 Agent (`investigation-agent`) 生成方案，但方案是交付给人类执行的文档，不是 Agent 自身的执行计划 |

**结论：Hermes 不是 Plan-and-Execute 架构。** 虽然存在"生成调查方案"这个行为，但方案是人类执行的操作手册，不是 Agent 自己的执行计划。Agent 不执行计划中的任何步骤。

### 2.3 Supervisor-Worker 模式 (CrewAI/AutoGen 风格)

Supervisor-Worker 模式的核心特征是：一个 Supervisor Agent（通常是 LLM）动态地将任务分配给不同的 Worker Agent。

```
典型 Supervisor-Worker:
  Supervisor: 这个案件需要取证分析和法律定性，先派取证专家
  Worker(取证专家): 完成取证，发现金额 500 万，涉及 3 人
  Supervisor: 取证完成，现在派法律分析专家
  Worker(法律分析专家): 根据取证结果，建议以职务侵占罪移送...
  Supervisor: 综合评估，决定移送司法机关
```

| 维度 | Supervisor-Worker 模式 | Hermes 架构 | 分析 |
|------|------------------------|-------------|------|
| **主控角色** | LLM Supervisor 动态决策 | 确定性 LangGraph StateGraph，阶段顺序固定 | ❌ 完全不同 |
| **任务分配** | Supervisor 决定谁做什么 | 阶段顺序是预设的，条件路由是确定性代码（如 `route_after_analysis`） | ❌ 完全不同 |
| **决策链路** | Supervisor 的 LLM 决策 → 无法完全追溯"为什么此时派这个 Agent" | 每步决策可追溯至具体代码和人工审批记录 | ❌ 完全不同 |
| **合规审计** | LLM 路由决策无法通过法律/人事决策的合规审计 | 完整审计链路：谁在什么时候做了什么，为什么 | ❌ 完全不同 |

**结论：Hermes 不是 Supervisor-Worker 架构。** 架构总则明确禁止"万能主 Agent"和"自主状态跳转权"。`01b-integrity-supervision-architecture-analysis.md` 中对方案 B（Supervisor 路由）的评估结论是"致命的法律风险不可接受"。

---

### 2.4 完全自主型 Agent (AutoGPT/Devin 风格)

完全自主型 Agent 接收一个高层目标，自主分解子任务、调用工具、处理错误、迭代直到目标完成。

| 维度 | 完全自主型 | Hermes 架构 |
|------|-----------|-------------|
| **自主性** | 极高 — 从目标到执行全程自主 | 极低 — Agent 只在指定阶段内生成结构化建议 |
| **工具权限** | 通常拥有广泛工具权限 | 每个 Stage Agent 只拿当前阶段必要工具，默认最小权限 |
| **错误处理** | Agent 自主决定重试策略 | 降级行为矩阵预定义，故障 → 进入人工接管不自动决策 |
| **终态写入** | Agent 直接修改系统状态 | Agent 输出必须经过 schema 校验、规则校验和人工守门 |
| **风险容忍** | 适合低风险场景（代码生成、信息检索） | 零容忍高风险决策自动化 |

**结论：Hermes 在自主性光谱上处于最低端。** 它在 AI Agent 社区中属于"AI 辅助决策"而非"AI 自主决策"系统。

## 三、Hermes 实际架构：三层递阶控制模型

### 3.1 架构全景

```text
┌──────────────────────────────────────────────────────────────────┐
│                     第 0 层：业务应用层                            │
│  API / 前端辛顿平台 / 风控系统                                      │
│  职责：创建业务命令、展示 AI 输出、收集人工反馈                      │
└──────────────────────────┬───────────────────────────────────────┘

                           ▼
┌──────────────────────────────────────────────────────────────────┐
│                   第 1 层：Module Graph（确定性主控）               │
│  LangGraph StateGraph / Checkpointer / 条件路由                   │
│  职责：阶段推进、HITL 触发、恢复、重试、回退循环、归档               │

│  ┌─────────────────────────────────────────────────────────────┐ │
│  │ 工作流阶段拓扑 (以廉洁监察为例):                                │ │
│  │                                                               │ │

│  │    │            ↑                 │              │            │ │

│  │    ├── END (不处理/转交)                         ├── END       │ │

│  │    └──→ enforcement ──→ post_report ──→ END       │            │ │

│  职责：生成结构化建议、证据摘要、报告初稿、风险判断                  │
```

### 3.2 三层职责的严格划分

| 层级 | 是否使用 AI | 能做什么 | 绝对不能做什么 |
|------|-----------|----------|---------------|
| **Module Graph** | 否，确定性代码 | 推进阶段、条件路由、触发 HITL、checkpoint、恢复、回退 | 不做业务判断、不生成内容 |
| **Stage Agent** | 是，LLM 调用 | 在单个阶段内生成结构化建议和证据引用 | 不推进阶段、不修改终态、不绕过 HITL |
| **HITL 守门** | 否，纯人工 | 确认通过、驳回重做、修改后通过、补充证据要求 | —（人类拥有最终裁决权） |

## 四、Stage Agent 内部架构模式分析

### 4.1 Stage Agent 不是 ReAct Agent

虽然 Stage Agent 内部调用了工具（如 RAG 检索、历史案例检索等），但它的运行模式与 ReAct 有本质区别：

**Hermes Stage Agent 的实际运行模式**：

```text
┌──────────────────────────────────────────────────────┐
│              单一推理周期（一次性完成）                  │
│                                                      │
│  输入 → 并行工具调用 → 结果聚合 → LLM 推理 → JSON 输出  │
│                                                      │
│  关键特征:                                            │
│  - 工具调用依赖图预定义（3-4 路并行，Agent 不选择）      │
│  - 一次 LLM 推理完成                                  │
│  - 不在思考-行动-观察中循环                            │
│  - 所有工具调用在 LLM 推理之前完成                      │
└──────────────────────────────────────────────────────┘
```

**对比 ReAct Agent 的典型运行模式**：

```text
┌──────────────────────────────────────────────────────┐
│           多轮循环（Agent 自主决定何时停止）             │
│                                                      │
│  Thought → Action → Observation → Thought → Action →  │
│  Observation → ... → Final Answer                     │
│                                                      │
│  关键特征:                                            │
│  - Agent 决定每轮调用什么工具                          │
│  - Agent 根据观察结果决定是否继续                      │
│  - 循环次数不确定                                      │
│  - 工具调用和 LLM 推理交替进行                         │
└──────────────────────────────────────────────────────┘
```

### 4.2 Stage Agent 内部状态机

每个 Stage Agent 都遵循一个内部状态机，但这是**执行流程的状态机**，不是推理循环：

```text
IDLE (等待输入)
  │
  ▼
KB_RETRIEVE / DATA_GATHER (并行工具调用)
  │
  ├── 成功 → EVIDENCE_ANALYZE / LLM_INFERENCE
  │            │
  │            ▼
  │         OUTPUT (生成结构化 JSON)
  │            │
  │            ▼
  │         PENDING_APPROVAL (等待碳基)
  │            │
  │      ┌─────┼─────┐
  │      ▼     ▼     ▼
  │   COMPLETE REJECTED REVISING
  │      │              │
  │      │         ┌────┘
  │      │         ▼
  │      │    KB_RETRIEVE (带修改意见，重新推理)
  │      │
  │      ▼
  │   流转到下一阶段
  │
  └── 失败 → LOW_CONF_WARNING (标记低置信度继续) / ERROR (降级/重试)
```

关键点：
- **不是推理循环**：状态转换由执行流程决定，不由 Agent 的内部推理决定
- **工具调用前置**：所有检索在一次并行调用中完成
- **单次 LLM 推理**：不是多轮 Reasoning + Acting
- **HITL 阻塞**：碳基守门是必须等待的外部事件

### 4.3 工具调用模式：预定义并行 + 结果聚合

以 `intake-agent` 为例，工具调用是预定义的并行图：

```text
Stage Agent 不决定调用什么工具 → 工具集由 Module Agent Profile 在阶段初预加载

实际执行:
  3 路并行检索（总耗时 = max(各路耗时)，不是 sum）:
  ├── kb_search_intake (4 子查询并行)
  │   ├── 组织架构
  │   ├── 制度法规（内部+外部）
  │   ├── 人员信息
  │   └── 供应商清单
  ├── es_search_similar_cases
  │   └── 基于案件描述全文检索历史案例
  └── audio_transcription_query
      └── 如果输入中有录音文件则查询

  聚合阶段:
  └── 合并检索结果 → 去重 → 结果校验 → 注入 LLM 上下文

  推理阶段:
  └── 单次 LLM 调用 → 生成结构化 JSON → Schema 校验
```

这种设计的好处是：
- **延迟可控**：不是串行的反复思考和行动，P50/P95/P99 都有明确预算
- **不产生 Agent 幻觉循环**：不会出现 LLM 错误地认为"还需要再查一下 X"导致无限循环
- **可测试**：每个工具可独立 mock 和测试

### 4.4 为什么不能给 Stage Agent 加 ReAct 循环

如果让 Stage Agent 拥有 ReAct 式自主工具调用循环，会带来以下风险：

| 风险 | 说明 |
|------|------|
| **延迟不可控** | Agent 可能进行不确定次数的工具调用，P95 延迟可能从 15s 膨胀到数分钟 |
| **工具越权** | Agent 可能在推理中尝试调用未授权的工具 |
| **幻觉循环** | LLM 可能错误地"发现"需要查询的新领域，产生不必要的检索 |
| **成本不可控** | Token 消耗和检索次数无法预算 |
| **审计困难** | "为什么 Agent 在第 3 轮决定查询 X"无法追溯至确定性规则 |

## 五、架构增强模式：Pipeline + 受控灵活度

### 5.1 当前架构的局限性（以廉洁监察为例）

`01b-integrity-supervision-architecture-analysis.md` 识别了纯 Pipeline 的三个核心缺陷：

| 缺陷 | 问题描述 | 影响 |
|------|----------|------|
| **证据不足无自动补救** | AnalysisAgent 发现证据不足时，只能等待人工发现并手动重启调查 | 案件停滞数天 |
| **简单案件也走全流程** | 轻微违规和重大舞弊走同样的 6 阶段流程 | 资源浪费 |
| **调查策略缺乏 AI 辅助优化** | 调查过程中发现新线索后无法动态调整方案 | 调查质量有提升空间 |

### 5.2 推荐增强方案：Pipeline + 证据驱动回退循环

```text
主干 Pipeline (确定性 LangGraph) — 保持不变:
  intake → investigation → analysis → disposition → enforcement
              ↑                 │
              │                 │ evidence_sufficiency = "insufficient"
              │                 │ AND loop_count < MAX (2)
              └─────────────────┘
              │
              │ 回退时携带: 缺失证据清单 + 建议调查方向 + loop_count++
              │
              │ evidence_sufficiency = "insufficient"
              │ AND loop_count >= MAX (2)
              ▼
         ESCALATED_TO_HUMAN (升级为人工决策)

并行辅助层 (只提建议，不控流程):
  ┌──────────────────────────────────────┐
  │ 调查策略顾问 (Investigation Advisor)    │
  │  - 并行运行，持续分析证据链完整性        │
  │  - 建议替代调查方向                     │
  │  - 输出必须经 HITL 审核后才生效         │
  │  - 权限: 只读                           │
  └──────────────────────────────────────┘
  ┌──────────────────────────────────────┐
  │ 案件复杂度评估器 (Complexity Assessor)  │
  │  - 在 intake 阶段并行运行               │
  │  - 评估: 金额/人数/跨部门/跨境/高管     │
  │  - 当前仅做信息展示，不改变路由          │
  └──────────────────────────────────────┘
```

### 5.3 增强方案的关键安全约束

```python
# 回退循环的安全守护
class EvidenceLoopGuard:
    max_loops: int = 2              # 最大回退次数
    loop_count: int = 0
    previous_evidence_gaps: list    # 记录之前的证据缺口，避免重复建议

    def can_loop_back(self) -> bool:
        return self.loop_count < self.max_loops

    def should_escalate(self) -> bool:
        """超过最大回退次数 → 升级为人工决策，不自动循环"""
        return self.loop_count >= self.max_loops
```

关键设计原则：
- **回退路由是确定性代码，不是 LLM 决策**：`route_after_analysis` 函数是 Python 代码，LLM 不参与路由选择
- **辅助 Agent 只有建议权**：输出走 HITL，不改变流程
- **最大回退次数硬限制**：防止无限循环
- **超限后升级为人工决策**：确保 AI 不会在没有人类介入的情况下反复循环

## 六、各模块 Agent 架构特征对比

### 6.1 两个核心模块的架构差异

| 维度 | 廉洁监察 (01) | 风险监控 (02) |
|------|-------------|-------------|
| **驱动方式** | 案件驱动（被动响应举报） | 定时调度（主动扫描，7×24） |
| **处理对象** | 单个高价值案件 | 海量业务数据 |
| **决策性质** | 法律定性 + 人员处罚 | 异常识别 + 风险分级 |
| **错误代价** | 极高 | 高 |
| **人工参与** | 每阶段必须（6 道 HITL 守门） | 仅高风险时需人工复核 |
| **Agent 数量** | 6 个 Stage Agent | 4 个 Stage Agent + 4 个哨兵 |
| **架构增强** | 证据驱动回退循环 + 调查策略顾问 | 智能异常哨兵（deep_analysis / rule_optimization / novel_risk / false_positive_sentinel） |
| **循环模式** | 支持回退循环（有最大次数限制） | 哨兵处理后继续向前（不循环） |
| **辅助 Agent** | 调查策略顾问（持续监控证据链） | rule-optimization-agent / novel-risk-agent |
| **运行周期** | 数天到数周 | 数分钟到数小时 |

### 6.2 风险监控的哨兵模式

风险监控模块引入了一种独特的**哨兵（Sentinel）模式**——旁路监控 Agent 在检测到异常模式时触发，但不改变主干 Pipeline 方向：

```text
主干 Pipeline:
  risk-rule → risk-scan → risk-merge → risk-classify → 结果推送
                  │                           │
                  │ (触发条件)                  │ (触发条件)
                  ▼                           ▼
        ┌─────────────────┐        ┌──────────────────────┐
        │ deep_analysis    │        │ rule_optimization     │
        │ _sentinel        │        │ _sentinel             │
        │                  │        │                       │
        │ 条件: AI初核      │        │ 条件: 误报率 > 30%     │
        │ uncertain比例     │        │ 或发现新型风险模式     │
        │ > 30%             │        │                       │
        │                  │        │ 动作: 标记风险规则     │
        │ 动作: 标记异常    │        │ 待优化 + 生成改进建议  │
        │ 批次深度分析      │        │                       │
        └─────────────────┘        └──────────────────────┘
                  │                           │
                  └───────────┬───────────────┘
                              │
                              ▼
                    继续主干流程 (不改变方向)
```

哨兵与主干的交互规则：
- 哨兵发现问题时**标记**风险/规则，不改变主干流向
- 哨兵的输出在下一次扫描周期中生效（规则优化 → 更新规则库 → 下次扫描使用新规则）
- 哨兵不直接修改规则库——修改必须经过人工审核

### 6.3 对话入口 Agent (09) 的特殊地位

`conversation-gateway-agent` 是唯一不完全遵循 Pipeline 模式的 Agent，因为它处于**流程之外**：

| 维度 | 业务 Stage Agent | conversation-gateway-agent |
|------|-----------------|---------------------------|
| **是否在 workflow 中** | 是，在指定阶段内 | 否，在 workflow 之前和之间 |
| **是否有阶段状态机** | 是 | 否，使用 Session 生命周期 |
| **是否生成业务输出** | 是 | 否，只生成意图和路由决策 |
| **权限范围** | 当前阶段工具集 | 只读查询 + 意图识别 |
| **架构模式** | Pipeline 中的单阶段节点 | 对话 + 结构化意图 + 路由（类似 Router Agent） |

它的架构可以理解为 **"前台解释层 Router Agent"**：

```text
用户自然语言
    │
    ▼
conversation-gateway-agent
    │
    ├── 意图识别 (L1/L2/L3 三层)
    ├── 缺失字段追问
    ├── 权限预检
    ├── 风险分级
    └── 路由决策:
        ├── answer_with_rag        → RAG Orchestrator
        ├── preview_action         → 展示确认卡片
        ├── handoff_to_api         → FastAPI
        ├── handoff_to_workflow    → LangGraph Runtime
        ├── handoff_to_stage_agent → 指定 Stage Agent (重生成)
        ├── deny                   → 权限拒绝
        └── human_intervention     → 人工接管
```

但它仍然受架构总则约束：不推进阶段、不修改终态、不绕过 HITL。

## 七、架构原则总结

### 7.1 六条硬约束（来自架构总则）

| # | 约束 | 目的 |
|---|------|------|
| 1 | 不得新增万能主 Agent | 防止 LLM 获得不受控的流程控制权 |
| 2 | 不得让 Agent 拥有全模块工具权限 | 最小权限原则，每个 Agent 只拿当前阶段必要工具 |
| 3 | 不得让 Agent 输出直接成为业务终态 | 必须经过 schema 校验、规则校验和人工守门 |
| 4 | 不得由 Worker 推进业务阶段 | Worker 只写任务结果，Workflow Runtime 负责 resume |
| 5 | 不得在 Prompt 中隐藏审批规则 | 审批逻辑必须是显式 workflow 规则 |
| 6 | 不得编造知识依据 | 检索不足时输出 `knowledge_insufficient`，进入人工接管 |

### 7.2 架构适合场景

| 适合 | 不适合 |
|------|--------|
| 高合规要求的业务流程（风控/审计/处罚/法务） | 开放域聊天 |
| 需要完整审计链路的决策 | 需要最大灵活性的探索性任务 |
| 错误代价极高的场景 | 快速原型验证 |
| 人工必须在关键节点裁决 | 完全自动化场景 |
| 多租户、多密级的数据隔离 | — |
| 需要严格 SLA（P50/P95/P99）的生产环境 | — |

### 7.3 如果要在其他系统复用这套架构

需要准备的要素：

1. **Module Graph**：LangGraph StateGraph + Checkpointer + 条件路由
2. **Module Agent Profile**：知识范围、工具权限、Prompt 包、模型路由、质量门禁
3. **Stage Agent**：单一阶段的结构化输出 Agent，预定义工具调用图
4. **HITL 机制**：每阶段的人工守门界面 + 驳回恢复机制
5. **Agent Runtime**：上下文装配、模型调用、schema 校验、trace 记录、降级处理
6. **RAG Orchestrator**：统一检索、权限过滤、混合召回、重排、引用追溯
7. **Model Gateway**：统一模型路由、熔断、备用切换

## 八、附录：主流 Agent 架构与 Hermes 对比速查表

| 架构模式 | 代表框架/系统 | 自主性 | 决策可追溯性 | 流程确定性 | 适合场景 | Hermes 是否采用 |
|----------|-------------|--------|-------------|-----------|---------|---------------|
| **ReAct** | LangChain ReActAgent | 中 | 中（思考链可记录） | 低（工具调用顺序不确定） | 信息检索、代码辅助 | ❌ |
| **Plan-and-Execute** | LangChain PlanExecuteAgent | 高 | 低（计划制定是AI决策） | 中（执行步骤固定但计划可变） | 自动化任务 | ❌ |
| **Supervisor-Worker** | CrewAI, AutoGen | 高 | 低（Supervisor是AI路由） | 低（任务分配是AI决策） | 多Agent协作 | ❌ |
| **完全自主型** | AutoGPT, Devin | 极高 | 极低 | 极低 | 开放式任务 | ❌ |
| **确定性Pipeline + Stage Agent + HITL** | **Hermes** | 极低（AI只在阶段内建议） | 极高（每步有代码规则+人工记录） | 极高（阶段顺序预定义） | 企业风控/审计/法务 | ✅ 当前架构 |
| **Pipeline + 回退循环** | **Hermes 增强方案** | 低（增加受控灵活度） | 高（回退是代码规则非AI决策） | 高（主干仍确定） | 需要有限灵活度的风控 | ✅ 推荐增强 |
