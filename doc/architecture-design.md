# 赫尔墨斯（Hermes）系统架构设计文档

---

## 一、架构概述

### 1.1 系统定位

赫尔墨斯（Hermes）是面向科沃斯集团的风险控制 AI 智能体系统，基于大语言模型（LLM）+ 检索增强生成（RAG）+ 多智能体协作（A2A）技术构建。系统覆盖风控业务全流程，集成**八大核心功能模块**，形成"**风险发现 → 调查分析 → 处置追责 → 整改闭环**"的完整风控链路。

**当前目标规模（主生产 Profile）**：支撑集团 **10,000 名注册/授权内部用户**、峰值 **500 并发会话/API 请求并发**，管理约 **10TB 文档数据**，处理海量多模态证据材料（音频/视频/图像/PDF），在保持低响应延迟（API P95 < 500ms，不含 LLM 推理）的同时，满足等保二级合规要求。

#### 部署 Profile 定义

本文档保留两套部署形态，所有容量、SLO、RPO/RTO、成本和运维要求均需标明适用 Profile。禁止将"10K 注册用户"误写为并发规模。

| Profile | 适用场景 | 规模口径 | 部署形态 | 可用性与恢复目标 |
|---------|----------|----------|----------|------------------|
| **P1: K8s 生产高可用** | 集团正式生产、跨部门持续使用、10TB 数据规模 | 10K 注册/授权内部用户；峰值 500 并发；10TB 文档数据 | Kubernetes 多节点 + PostgreSQL Patroni + Redis/RabbitMQ/MinIO/ES 集群 | API 99.9%；DB 主库故障 RPO < 5min / RTO < 15min；DB 集群全故障 RPO < 1min / RTO < 2h；站点灾难 RPO < 1h / RTO < 4h |
| **D0: 本地/测试 Docker Compose** | 本地开发、测试环境、PoC、演示和容量验证 | 100 用户测试规模；峰值 30 并发以内；5TB 以下测试/脱敏数据 | 单机 Docker Compose；可选备份主机/备份磁盘 | 不作为生产 SLA 承诺；每日备份恢复目标仅用于演练参考 |

### 1.2 核心架构能力

| 维度 | 能力描述 |
|------|----------|
| **工作流编排** | 基于 LangGraph 的有状态工作流引擎，支持条件路由、断点续跑、人工守门（Human-in-the-Loop） |
| **知识增强** | 基于 PGVector 的多分区向量检索（RAG），每个业务阶段挂载独立知识库索引；混合检索（向量 + Elasticsearch 全文） |
| **多智能体协作** | 通过 A2A（Agent-to-Agent）协议与龟宝（HR）、西塞罗（法务）、波特（财务）协同；基于 RabbitMQ 的消息总线保证可靠投递 |
| **外部系统集成** | 与风控系统、OA 系统（BPM）、MDM 主数据管理系统的双向数据同步；消息队列驱动 + 熔断器保护 |
| **异步优先架构** | 基于 RabbitMQ 消息队列的全异步处理架构，用户操作立即返回（< 100ms），长耗时任务（多模态处理、报告生成、外部同步、LLM 推理）后台执行（返回 task_id + WebSocket 进度推送）；支持重试、死信、优先级队列 |
| **多模态处理管道** | 独立处理管线：音频（Whisper ASR + 说话人分离）、图像（PaddleOCR + CLIP 分类）、视频（OpenCV 关键帧 + 场景分析）、文档（unstructured.io PDF/Office 解析）；GPU 加速处理 |
| **数据分层存储** | 三层热温冷数据分级：热数据（活跃案件 < 90天）存 PostgreSQL + pgvector；温数据（近期归档 90天-2年）存 MinIO 对象存储；冷数据（历史 > 2年）存 NAS/磁带归档；自动迁移策略 + 可搜索元数据索引 |
| **水平弹性伸缩** | 所有服务均无状态设计，基于 Kubernetes 自动扩缩容；API 层 3-20 实例（HPA）；Worker 按任务类型分 9 个独立池独立扩缩 |
| **CDN 与缓存** | Nginx 缓存层 + Redis Cluster 提供文档预览/缩略图 CDN 分发；热点查询缓存加速（5min TTL）；视频 HLS 自适应码率分段流 |
| **可观测性** | LangFuse + Prometheus + structlog + Jaeger 四层监控体系，覆盖 LLM 调用、API 性能、分布式追踪、业务指标。Grafana 统一仪表板 |
| **分层记忆** | L1 感知记忆 (即时上下文) → L2 会话记忆 (多轮对话) → L3 案例记忆 (案件全生命周期) → L4 组织记忆 (跨案件知识沉淀)。记忆从短到长逐层固化，支持跨案件学习与经验复用 |

## 二、设计原则

### 2.1 架构原则

| 原则 | 说明 | 落地方式 |
|------|------|----------|
| **关注点分离 (SoC)** | 业务模块独立部署，共享基础设施横向复用 | 8 个业务模块各自维护独立的 LangGraph 子图；共享认证、知识库、审计日志等横切服务 |
| **人机协同 (HITL)** | 每个工作流阶段碳基守门，AI 辅助决策、人工最终确认 | LangGraph `interrupt_before` 机制在每个阶段节点前挂起等待人工审批 |
| **有状态工作流** | 支持案件断点续跑、阶段回溯、人工介入后恢复 | Redis Cluster-based Checkpointer 持久化工作流状态，支持 LangGraph thread 级别恢复 |
| **知识驱动** | 各阶段决策基于结构化知识库而非仅依赖 LLM 参数记忆 | PGVector 多分区向量检索 + Elasticsearch 混合检索，每阶段注入对应知识库上下文到 LLM Prompt |
| **协议解耦** | 外部系统通过 Adapter 模式隔离，不直接耦合 | 风控系统、OA、MDM、A2A 均通过独立 Adapter 封装，支持协议变更时最小化影响面 |
| **安全内建 (Security by Design)** | 等保二级要求嵌入架构设计而非事后修补 | JWT + RBAC + AES-256-GCM 字段加密 + 全量审计日志 + 软删除 |
| **弹性设计** | 关键节点失败自动重试，不可恢复时降级至人工接管 | 每个 StageNode 定义 max_retries 和 timeout；RabbitMQ 消息队列保证异步可靠性 + 死信队列 |
| **异步优先 (Async-First)** | 所有重计算操作（多模态处理、报告生成、外部同步、LLM 推理）异步执行，用户 API 立即返回 task_id | 基于 RabbitMQ 的消息驱动架构，9 类独立 Worker Pool（audio/image/video/doc/report/sync/a2a/llm/kb）；用户通过 WebSocket 或轮询获取结果 |
| **数据分层 (Data Tiering)** | 按数据访问频率和生命周期分层存储，控制热存储成本 | 热层（活跃案件 < 90天）：PostgreSQL 主库 + pgvector；温层（近期归档 90天-2年）：MinIO 对象存储；冷层（历史 > 2年）：NAS/磁带归档；自动迁移策略与可搜索元数据索引 |
| **水平扩展 (Horizontal Scale)** | 所有服务无状态，独立水平扩展 | API 层：K8s HPA 自动扩缩 3-20 实例；Worker 层：按任务类型独立 Pod 池扩缩；数据库：主从读写分离 + 2 读副本 |
| **多模态管道 (Multimodal Pipeline)** | 每种媒体类型独立处理管线，充分利用 GPU 加速，处理结果统一索引 | 音频管道（Whisper + 说话人分离）；图像管道（PaddleOCR + CLIP 分类）；视频管道（OpenCV 关键帧 + 场景分析）；文档管道（unstructured.io PDF/Office 解析） |
| **渐进加载 (Progressive Loading)** | 大文件不阻塞用户交互，先预览后加载 | 文档缩略图预生成 + 分页流式加载；视频 HLS 分段传输；音频流式播放；文件 Range 分段下载 |
| **渐进交付** | 支持按模块分期实施，共享基础设施先行 | Phase 1 先交付基础骨架 + 廉洁监察模块 + 基础设施升级（K8s/消息队列/ES）；其余模块基于共享底座按需扩展 |

### 2.2 关键架构决策 (ADR)

| ADR # | 决策 | 理由 | 替代方案（已否决） |
|-------|------|------|-------------------|
| ADR-001 | 使用 LangGraph 而非自研工作流引擎 | 原生支持 Checkpointer、interrupt、条件路由、streaming；LangChain 生态集成 | 自研状态机（维护成本高）；Temporal（过重，不适合 LLM 工作流） |
| ADR-002 | PGVector 而非独立向量数据库 | 减少运维复杂度；与业务数据共库，支持事务一致性；pgvector 0.7+ HNSW 索引性能已满足规模需求（配合索引优化与分区） | Milvus（部署重）；Pinecone（SaaS 外部依赖） |
| ADR-003 | RabbitMQ + Celery 替换原有 Celery + Redis 直接架构 | 10K 注册用户/峰值 500 并发下需要可靠的消息持久化、quorum queues、消息优先级、死信队列（DLX）、联邦支持；RabbitMQ 提供企业级可靠性 | Redis 直接做队列（持久化弱，无原生优先级）；Kafka（日志语义，不适合任务队列场景） |
| ADR-004 | DeepSeek 为主 LLM，通义千问为备 | DeepSeek 中文能力优秀，API 兼容 OpenAI 格式，成本可控；通义千问作为降级备份 | GPT-4（成本高）；文心一言（API 兼容性差） |
| ADR-005 | 知识库离线本地管理，无飞书 API 依赖 | 等保要求数据不出内网；离线管理满足知识库低频更新场景 | 飞书 API 同步（外部网络依赖） |
| ADR-006 | Elasticsearch 作为全文搜索引擎 | 10TB 文档规模下，PostgreSQL 全文检索无法满足 P95 < 200ms 要求；ES 提供分布式倒排索引 + IK 中文分词 + 聚合分析 | PostgreSQL FTS（扩展性不足）；Solr（社区不如 ES 活跃） |
| ADR-007 | PaddleOCR 为中文 OCR 引擎（自部署） | 中文场景准确率 > Tesseract；支持表格识别、印章检测、版面分析；GPU 加速；纯内网部署，满足等保要求 | Tesseract（中文弱）；百度 OCR API（外部依赖） |
| ADR-008 | Whisper large-v3（自部署）为语音转文字引擎 | 开源、多语言支持、GPU 加速、可批量离线处理；1 小时音频 < 5 分钟处理（V100 GPU） | 阿里云语音识别（外部依赖、按量计费）；讯飞（API 限额） |
| ADR-009 | Kubernetes 替代 Docker Compose | P1 Profile 的 10K 注册用户、峰值 500 并发和 10TB 数据规模需要自动扩缩容、滚动更新、健康检查、资源调度；Docker Compose 仅适合单机原型验证 | Docker Swarm（功能弱）；Nomad（生态小） |
| ADR-010 | Jaeger 分布式追踪 | 微服务化后需要跨服务调用链追踪，Jaeger 支持 OpenTelemetry、采样策略灵活（正常 10%，错误 100%） | Zipkin（功能类似但社区不如 Jaeger 活跃）；SkyWalking（偏 Java 生态） |

### 4.2 模块一：廉洁监察（反舞弊调查）✅ 已实现

**职责**：接收双轨案件来源（系统抓取 + 人工录入），通过 6 阶段 AI 辅助工作流完成从线索初判到报案协助的全流程反舞弊调查。

**工作流阶段**：

```
案件录入 → [4.1] 材料初判+分流 → [4.2] 调查方案 → [4.3] 多维分析+报告
                                        ↓
         [4.6] 报案协助 ← [4.5] 处罚执行 ← [4.4] 处置分流+追责
```

**状态定义** (`HermesState`)：包含案件基础信息（task_id, fraud_source, client）、工作流控制（current_stage, stage_history）、分流决策（should_investigate, is_hr_related）、各阶段 AI 输出（intake_report, case_conclusion, penalty_opinion）、碳基守门状态（pending_approval_stage, approval_result）、外部系统状态（risk_control_sync_status, a2a_task_ids）。

**外部交互**：
- 风控系统：字段映射同步（fraudSource ↔ reportedStaffName 等双向映射），WebSocket 状态推送
- A2A 龟宝：HR 案件转交、员工处罚跟踪回传
- A2A 西塞罗：民事纠纷推送、处罚协议审核
- A2A 波特：供应商扣款跟踪
- OA 系统：添可事业部处罚公告审批推送
- MDM：涉案供应商黑名单维护

**多模态数据**：

| 数据类型 | 来源 | 处理方式 | 预估量/案件 | 存储层 |
|----------|------|----------|------------|--------|
| 音频 (访谈录音) | 调查访谈 | Whisper ASR → 文本 → ES+PGVector | 30-120min (300-1200MB) | 热层(活跃)→温层(归档) |

### 4.3 模块二：风险监控（主动风险扫描）⏳ 规划中

**职责**：实现 7×24 小时无人值守自动风险监控，从规则生成到异常数据捕获、分析定性、自动推送的全链路主动扫描。

**工作流阶段**：

```
[6.1] 风险规则清单生成 → [6.2] 异常数据生成 → [6.3] 风险分析与主体合并
                                                   ↓
[6.6] 处置回流与指标迭代 ← [6.5] 风险结果推送 ← [6.4] 风险自动定性
```

**核心能力**：
- AI 自动生成风险场景 → 计算规则 → SQL 语句，测试环境验证后可入库
- 双重校验机制：AI 初核（剔除正常业务）+ 人工二次复核
- 按分析主体自动合并重复预警，统一口径
- 自动判定风险类型（合规风险/舞弊风险/商业秘密风险）、等级、处置建议
- 处置结果回流至知识库，持续优化规则准确率

**外部依赖**：业务数据库（SQL 查询）、企查查工商信息、舆情信息、外部法律法规

**多模态数据**：

| 数据类型 | 来源 | 处理方式 | 预估量/天 | 存储层 |
|----------|------|----------|----------|--------|
| 结构数据 (DB扫描) | 业务系统SQL查询结果 | 直接入库分析 | 1-5GB 结果集 | 热层 |
| 图像 (证据附件) | 异常推送附带截图 | OCR + 分类 | 10-50 张 (20-100MB) | 热层→温层 |
| 文档 (外部报告) | 企查查报告/舆情报告 | 文档解析 + 索引 | 5-10 份 (5-20MB) | 温层 |

### 6.3 HPA 扩缩容策略

```
  自动扩缩 (HPA - Horizontal Pod Autoscaler):
  API 服务:
  ├── 指标: CPU > 70% 持续 2min → 扩容 +2
  ├── 指标: 请求延迟 P95 > 500ms 持续 2min → 扩容 +2
  ├── 指标: CPU < 30% 持续 10min → 缩容 -1
  ├── 冷却: 扩容 1min / 缩容 5min
  └── Pod Disruption Budget: minAvailable=2

  Worker 服务 (通用):
  ├── 指标: RabbitMQ 队列深度 > 阈值 → 扩容 +1
  ├── 指标: 队列深度 < 阈值/2 持续 10min → 缩容 -1
  └── GPU Worker: GPU 资源稀缺，优先保留而非缩容

  定时扩缩 (CronHPA):
  ├── 工作日 8:00 → API 预热到 5 副本 (应对上班高峰)
  ├── 工作日 9:00-12:00 → API 保持 8-20 副本 (核心工作时段)
  ├── 工作日 20:00 → API 缩容到 3 副本 (非工作时间)
  ├── 周末/节假日 → API 保持 2 副本 (风险监控 7x24)
  └── 风险监控 Worker: 7x24 最少 1 副本，工作日峰值 3 副本
```

**K8s 运行治理基线（P1 Profile 必备）**：

| 治理项 | 要求 |
|--------|------|
| Namespace/RBAC | `hermes-prod`、`hermes-staging`、`hermes-dev` 独立 Namespace；ServiceAccount 最小权限；禁止业务 Pod 使用 cluster-admin |
| ResourceQuota/LimitRange | 每个 Namespace 配置 CPU/内存/GPU 配额与默认 requests/limits，避免无界资源消耗 |
| PDB/反亲和 | API、Worker、PgBouncer、RabbitMQ、Redis、ES、MinIO 均配置 PodDisruptionBudget；关键副本跨节点反亲和或 TopologySpread |
| GPU 调度 | GPU 节点使用 taint/toleration 与 nodeSelector；仅 audio/image/video worker 可申请 GPU |
| 存储 | StatefulSet 使用明确 StorageClass 与 PVC；PG/ES/Redis/RabbitMQ/MinIO 禁止使用 emptyDir 持久化 |
| 探针 | API/Worker 暴露 liveness/readiness/startup probe；依赖不可用时 readiness 失败、liveness 不盲目重启 |
| 弹性指标 | API 使用 HPA（CPU/内存/延迟）；Worker 使用 KEDA 读取 RabbitMQ 队列深度；容量触发阈值见 §8.16 |
| 维护窗口 | 节点 drain 前先确认 PDB、备份状态和队列积压；生产节点升级需灰度并保留回滚窗口 |

### 6.5 数据库集群配置

```
  PostgreSQL 16 集群 (Patroni + Streaming Replication + PgBouncer):
  Patroni 管理 Primary 自动选主与故障转移
  Primary (8C/32G/2TB) → WAL Streaming → Replica-1 (8C/32G/2TB)
                                        → Replica-2 (8C/32G/2TB)
  PgBouncer:
  ├── write pool: 路由到当前 Patroni primary
  └── read pool: 路由到健康 replica；故障时临时回退 primary
  分区策略:
  ├── cases:      按 created_at RANGE 分区 (年)
  ├── audit_logs: 按 created_at RANGE 分区 (月)
  ├── case_evidences: 按 case_id HASH 分区
  └── kb_chunks:  按 kb_type LIST 分区 + 按年子分区

  索引策略:
  ├── B-tree: 高频查询字段 (case_id, user_id, status)
  ├── GIN: JSONB 字段, 全文检索字段
  ├── HNSW: pgvector 向量索引 (kb_chunks 表)
  └── 部分索引: 仅活跃状态的案件索引

  备份策略:
  ├── pgBackRest 全量/增量备份 → MinIO + NAS 双副本
  ├── WAL 连续归档 → MinIO（异地副本）
  ├── PITR: 支持任意时间点恢复 (保留 30 天 WAL)
  ├── 每季度执行恢复演练并记录实际 RPO/RTO
  └── pg_basebackup 仅用于新副本初始化或人工修复，不作为生产主备份方案
```

#### 7.3.2 A2A 任务消息协议（统一格式）

```json
{
  "schema_version": "a2a.task.v1",
  "event_id": "uuid",
  "task_id": "uuid",
  "correlation_id": "trace/task correlation id",
  "idempotency_key": "target_agent:command:case_ref:payload_hash",
  "source_agent": "hermes",

  "callback_queue": "hermes.a2a.callback.{agent}",
  "created_at": "ISO8601",
  "expires_at": "ISO8601 (TTL 24h)",
  "retry_count": 0,
  "signature": "HMAC-SHA256 over canonical body"
}
```

**消息契约与重放规则**：

| 项 | 规则 |
|----|------|
| 版本 | 所有 A2A 和内部事件必须带 `schema_version`；同一主版本内只允许向后兼容新增字段 |
| 幂等 | 生产同时使用 Redis TTL 去重和 PostgreSQL Inbox 落库；Redis 失效不影响长期去重审计 |
| Outbox | 业务事务内写入 Outbox，后台发布到 RabbitMQ；发布成功后标记 `published_at` |
| DLQ | poison message 进入 DLQ 后保留 30 天；P1 需在 4 小时内确认处理策略 |
| Replay | 重放必须指定 `event_id` 范围、操作者和原因；重放动作写入 audit_log |
| Webhook | 外部回调必须校验 HMAC 签名、时间戳窗口和来源 IP 白名单 |

| 安全域 | 需求项 | 实现方式 |

| **身份鉴别** | 用户身份唯一标识与验证 | P1 接入企业 SSO/OIDC/AD；JWT 令牌机制，Access Token 8h/Refresh Token 7天；失败 5 次锁定 30 分钟；关键操作启用 MFA；Token 黑名单 (Redis Cluster 全局同步) |

| **数据保密性** | 敏感字段加密存储 | AES-256-GCM 列级加密（姓名/电话/邮箱）；P1 密钥由 Vault/External Secrets 注入；MinIO SSE-S3 文件加密 |
| **数据分级保护** | 10TB 数据分类管控 | 密级标记：公开/内部/秘密/机密四级；敏感文件访问独立审计；机密级下载需风控负责人审批 |
| **AI 安全** | 防止 LLM 越权和幻觉 | Prompt 注入防护、RAG 租户过滤、Tool 权限矩阵、法规/证据引用强制校验；高风险输出进入人工复核 |

| **工作流中断** | Redis Checkpointer 持久化；thread_id 精确恢复 | < 10s | 无降级 |
| **节点故障** | K8s liveness probe 自动重启不健康 Pod | < 30s | Pod 迁移到健康节点 |

### 8.8 数据生命周期管理

| 阶段 | 触发条件 | 迁移动作 | 存储介质 | 访问 SLA |
|------|----------|----------|----------|----------|
| **热层 (Hot)** | 案件创建至关闭后 90 天 | — | PostgreSQL + pgvector | P95 < 50ms (索引) / < 200ms (复杂) |
| **热→温** | 案件关闭后 90 天 | 案件完整数据打包 → MinIO；PG 中保留元数据指针和摘要；原始大文件从 PG 删除 | MinIO 对象存储 | P95 < 200ms (元数据) / < 1s (文件下载) |
| **温→冷** | 案件关闭后 2 年 | 案件 + 证据 + 报告完整打包 → NAS/磁带；MinIO 中删除；ES 索引保留可搜索元数据；PG 仅保留案件号、归档路径、关键词 | NAS / 磁带 | 按需恢复：< 24h |
| **冷保留** | 冷层已存储 | 保留 10 年（法规要求） | NAS / 磁带 | 按需恢复 |
| **到期清理** | 超过 10 年 | 审批后物理销毁 | — | — |

**自动化机制**：
- 每日定时任务扫描案件状态：`status=closed AND closed_at < now() - 90days` → 热→温迁移
- 每周定时任务：`closed_at < now() - 2years` → 温→冷迁移
- 冷恢复流程：用户 API 请求 → 后台创建恢复任务 → 机器人从磁带提取 → 暂存 MinIO → 通知用户下载 (7 天有效期)
- 迁移日志完整记录到 audit_log

### 8.10 零停机数据库迁移策略

| 迁移类型 | 策略 | 示例 | 风险等级 |
|----------|------|------|----------|
| **新增表** | 直接执行，无影响 | `CREATE TABLE new_feature (...)` | 低 |
| **新增列 (可空)** | 直接执行；应用代码先兼容新列，再填充数据 | `ALTER TABLE ADD COLUMN x TEXT` | 低 |
| **新增列 (非空+默认值)** | 分三步：① 加可空列 + 默认值填充 ② 数据回填 ③ 改 NOT NULL | `ALTER TABLE ADD COLUMN status VARCHAR DEFAULT 'pending'` | 中 |
| **修改列类型** | 新增列 → 双写 → 回填 → 切换读取 → 删除旧列 | `VARCHAR(50)` → `VARCHAR(100)` | 高 |
| **删除列/表** | 先标记废弃 (应用代码不再读写) → 下一版本删除 | 软删除周期：至少 1 个版本 | 高 |
| **索引变更** | PostgreSQL `CONCURRENTLY` 模式 (不锁表) | `CREATE INDEX CONCURRENTLY idx_xxx ON t(c)` | 低 |
| **数据迁移** | Celery 异步任务分批处理 (1K/批, 间隔 100ms) | 历史数据重新分块 → Embedding | 中 |

**迁移执行流程**：
1. Alembic 生成迁移脚本 → Code Review (重点: 锁表风险、回滚方案)
2. Staging 环境验证 (使用生产数据量级模拟)
3. 生产维护窗口执行 (凌晨 2:00-4:00，或 CONCURRENTLY 随时执行)
4. 预检查: `SELECT pg_size_pretty(pg_database_size('hermes'))`, 磁盘剩余 > 30%
5. 迁移执行 + 监控 (长时间锁检测告警: > 10s)
6. 验证: 冒烟测试套件 (10 个核心 API)

**回滚边界**：生产数据库迁移不以"恢复上一版本 DB 快照"作为常规回滚手段。低/中风险迁移必须提供前滚修复脚本；高风险迁移必须提供双写/回填/切读方案、只读验证步骤、人工审批和暂停条件。

### 8.12 API 版本管理策略

| 策略 | 说明 |
|------|------|
| **版本格式** | URL 路径版本: `/api/v1`、`/api/v2` |
| **兼容性承诺** | 同一主版本内向后兼容 (不删除字段、不修改字段类型)；新增字段可接受 |
| **弃用流程** | ① 新版 API 上线 → ② 旧版标记 `Deprecated` (响应头 + 文档) → ③ 6 个月过渡期 (监控旧版调用量) → ④ 调用方迁移完毕 → ⑤ 旧版下线 |
| **破坏性变更** | 仅在新主版本引入 (如 `/api/v2`)；旧版本并行运行至少 6 个月 |
| **文档同步** | OpenAPI 3.0 自动生成 (FastAPI 内置)，Swagger UI 实时查看；版本间差异用 `@deprecated` 标记 |

### 8.13 多租户数据隔离方案

系统涉及三个法人实体（科沃斯、添可、集团），需在共享基础设施上实现数据隔离：

| 维度 | 隔离方式 | 实现 |
|------|----------|------|
| **数据库层** | 共享数据库 + PG RLS 行级隔离 | 所有租户相关表包含 `client` 字段 (`ecovacs` / `tineco` / `group`)；P1 生产默认启用 Row-Level Security |
| **应用层** | RBAC 三层角色 + 查询自动注入 | API 中间件自动注入 `WHERE client = $current_user_role`；`group` 角色仅在显式全局权限下跳过过滤 |
| **文件存储** | MinIO Bucket 按 client 分区 | `hermes-ecovacs` / `hermes-tineco` / `hermes-group` 三个独立 Bucket |
| **搜索索引** | ES 索引按 client 别名 | `hermes-docs-ecovacs` / `hermes-docs-tineco` / `hermes-docs-group`；搜索时自动路由 |
| **缓存** | Redis key 前缀隔离 | `ecovacs:cache:...` / `tineco:cache:...` / `group:cache:...` |
| **审计** | 审计日志记录 client 上下文 | 每条日志标记 `client` 字段，支持按租户独立审计 |

> 隔离原则：科沃斯用户不可查询添可数据，反之亦然。集团用户拥有全局视角但必须有显式全局权限。P1 Profile 使用应用层过滤 + PG RLS 双保险，禁止只依赖应用层拦截。

### 8.14 智能体记忆架构设计

记忆是 AI 智能体区别于传统规则系统的核心能力。赫尔墨斯的记忆体系采用**分层记忆架构**，覆盖从单次交互到跨案件学习的完整记忆谱系。

#### 8.14.1 记忆分层模型

```
┌─────────────────────────────────────────────────────────────────┐
│                    赫尔墨斯记忆分层架构                             │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L4: 组织记忆 (Organizational Memory)                        │ │
│  │  跨案件/跨用户/跨模块的持久知识                                │ │
│  │  ├── 知识库 (RAG): 制度法规、历史案例、报告模板、风险规则      │ │
│  │  ├── 反馈闭环: 处置结果回流 → 规则优化 → 知识更新             │ │
│  │  └── 审计日志: 全量操作记录，支撑复盘与模式发现               │ │
│  │  存储: PGVector + Elasticsearch + PostgreSQL                 │ │
│  │  生命周期: 永久 (持续更新)                                    │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 固化                               │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L3: 案例记忆 (Episodic Memory)                              │ │
│  │  单个案件的完整处理轨迹与决策链                                │ │
│  │  ├── 案件工作流状态 (LangGraph State + Checkpointer)          │ │
│  │  ├── 阶段产出物 (初判报告/调查方案/分析报告/追责意见)          │ │
│  │  ├── 碳基守门记录 (审批决策/修改内容/驳回原因)                 │ │
│  │  └── 外部交互记录 (A2A 任务/风控同步/法务回传)                │ │
│  │  存储: Redis (活跃) + PostgreSQL (持久)                       │ │
│  │  生命周期: 案件活跃期 → 温层归档 (90天) → 冷层 (2年+)        │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 聚合                               │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L2: 会话记忆 (Conversational Memory)                        │ │
│  │  单个工作流阶段内的多轮人机交互上下文                           │ │
│  │  ├── LLM 对话历史 (messages: BaseMessage[])                  │ │
│  │  ├── 检索上下文 (本轮 RAG 召回的文档片段)                      │ │
│  │  ├── Tool 调用结果缓存 (避免重复计算)                         │ │
│  │  └── Context Window 管理 (摘要压缩 + 滑动窗口)                │ │
│  │  存储: Redis (热) + LangGraph State (序列化)                  │ │
│  │  生命周期: 单阶段 (守门完成后归档 → 压缩摘要保留)              │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 交互                               │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L1: 感知记忆 (Sensory Memory)                               │ │
│  │  单次 LLM 调用的即时输入                                       │ │
│  │  ├── 用户输入 (文本/字段/附件引用)                             │ │
│  │  ├── 多模态感知结果 (ASR 转录/OCR 文本/视频描述)               │ │
│  │  └── 系统注入 (System Prompt + 阶段知识 + 历史摘要)           │ │
│  │  存储: LLM Context Window (瞬时, 无持久化)                    │ │
│  │  生命周期: 单次 LLM 调用结束即释放                             │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

#### 8.14.2 记忆流转与生命周期

```
用户操作 → L1 感知记忆 ──LLM推理──→ L2 会话记忆 (多轮对话)
                                        │
                        ┌───────────────┘ 守门通过
                        ↓
                  L3 案例记忆 (阶段产物 + 决策链)
                        │
            ┌───────────┼───────────┐
            ↓           ↓           ↓
       后续阶段引用   问题汇入     相似案件推荐
       (继续调查)   持续改善模块   (风险监控回流)
                        │
                        ↓ 案件闭环
                  ┌─────────────────┐
                  │   L3 → L4 固化   │
                  │                  │
                  │  调查报告 → 案例库│
                  │  处置经验 → 规则库│
                  │  缺陷模式 → 指标库│
                  └─────────────────┘
```

#### 8.14.3 记忆检索策略

| 记忆类型 | 检索方式 | 触发时机 | 技术实现 |
|----------|----------|----------|----------|
| **L4 组织记忆** | 向量语义检索 + 全文关键词 + 结构化过滤 | 每个工作流阶段启动时 | PGVector (cosine similarity) + ES (BM25) + SQL (元数据过滤)；混合检索 + Re-ranking |
| **L3 案例记忆** | 结构化查询 + 相似案例检索 | 调查方案生成 / 案件定性 / 追责建议时 | SQL 查询历史案件 (同类型/同部门/同金额区间)；PGVector 相似案例召回 |
| **L2 会话记忆** | LangGraph State 直接读取 | 单阶段内后续 LLM 调用 | `state["messages"]` 自动注入；超长对话自动摘要压缩 (LLM 生成 200 token 摘要) |
| **L1 感知记忆** | 实时注入 | 每次 LLM 调用 | System Prompt 模板 + 阶段知识注入 + RAG 上下文组装 |

#### 8.14.4 上下文窗口管理策略

针对 LLM 上下文窗口有限（DeepSeek 64K tokens）的问题：

| 策略 | 触发条件 | 处理方式 |
|------|----------|----------|
| **滑动窗口** | messages 总 token > 32K | 保留最近 16K tokens + System Prompt + 早期摘要 |
| **自动摘要** | 单阶段对话超过 10 轮 | LLM 生成 200 token 结构化摘要（关键事实/决策/待办），替换早期详细对话 |
| **分层注入** | 每阶段启动 | System Prompt (固定) → 阶段知识 (RAG top 5, ~2K tokens) → 历史摘要 (~500 tokens) → 用户输入 |
| **引用而非复制** | 引用大段文档内容 | 仅保留文档 ID + 相关片段引用，完整文档按需再次检索 |

#### 8.14.5 跨案件学习闭环

```
案件 A (已完成) ──→ 案例记忆 (L3)
                        │
            ┌───────────┼───────────┐
            ↓           ↓           ↓
       调查报告入库   处罚经验提取   缺陷模式识别
       (案例库更新)   (规则库更新)   (指标库更新)
            │           │           │
            └───────────┼───────────┘
                        ↓
              组织记忆 (L4) 更新
                        │
            ┌───────────┼───────────┐
            ↓           ↓           ↓
       案件 B         风险监控      内控评价
       (调查方案     (规则命中率    (缺陷识别
        自动引用      提升)         更精准)
        先例)
```

**固化机制**：
- **自动固化**：案件闭环后，调查报告 + 关键决策 + 处置结果自动入库（结构化特征提取 + Embedding 索引）
- **人工审核**：高风险案件（涉及刑事/重大金额）需人工审核后入库
- **衰减/淘汰**：过时案例（法律法规已变更）标记为"仅供参考"，权重降低
- **指标迭代**：风险监控模块的处置结果回流 → 误报规则优化 → 准确率持续提升（已体现在 风险监控 [6.6] 阶段）

### 8.16 SLO/SLI 定义与容量规划

#### SLO 指标定义

| 服务 | SLI | SLO | 测量窗口 | 告警阈值 |
|------|-----|-----|----------|----------|
| **API 可用性** | 成功请求数 / 总请求数 (2xx/3xx) | ≥ 99.9% | 30 天 | < 99.5% → P1 |

### 8.19 知识库初始化策略

#### 8.19.1 冷启动风险

RAG 系统的质量高度依赖知识库的丰富程度。一个空的知识库上线后，LLM 缺乏上下文支撑，将出现以下问题：

- **初判准确率低**：没有历史案例参考，LLM 倾向给出通用判断
- **调查方案质量差**：无法匹配类似案件的成功调查路径
- **法规引用不可靠**：没有制度法规注入，LLM 可能"幻觉"出不存在的规定
- **用户体验差**：首次使用即遭遇低质量输出，用户信任难以建立

#### 8.19.2 初始化阶段与数据源

**Phase 0：上线前 2 个月 — 基础数据采集**

### 8.20 应急预案

#### 8.20.1 应急响应等级

| 等级 | 定义 | 响应时间 | 通知范围 | 处理人 |
|------|------|----------|----------|--------|
| **P0 紧急** | 核心功能完全不可用（API 全宕/DB 损坏/数据泄露） | < 15min | 全员通知 | 技术负责人 + 风控负责人 |
| **P1 严重** | 部分功能不可用或性能严重下降（LLM 不可用/搜索不可用/用户无法登录） | < 30min | 受影响用户群 | 技术负责人 |

#### 8.20.2 场景化应急 SOP

**SOP-01: LLM（DeepSeek）不可用**

```
现象: LLM 调用持续返回 5xx 或超时（> 30s），持续 5 分钟以上
影响: 所有 AI 功能不可用（初判/报告生成/智能分析）

处理步骤:
1. [5min]  确认故障范围：检查 DeepSeek Status Page（status.deepseek.com）
2. [2min]  执行切换：修改 LLM_API_BASE → 通义千问 API
   export LLM_MODEL=qwen3.7-plus
   curl -X POST localhost:8000/api/v1/admin/switch-llm -d '{"provider":"qwen"}'
3. [5min]  验证：调用 /api/v1/health/llm 确认备用 LLM 可用
4. [持续]  监控：关注 Qwen API 调用成功率和响应时间
5. [恢复]  DeepSeek 恢复后，观察 30 分钟稳定，切回
6. [事后]  复盘报告：故障时长、影响范围、改进措施

降级行为: 用户操作不受影响（数据查看、守门审批等非 AI 功能正常）
恢复目标: < 5min（自动切换）/ < 15min（手动切换）
```

**SOP-02: 数据泄露事件**

```
现象: 发现未经授权的数据访问或数据外传
影响: 合规风险，可能触发等保违规

处理步骤:
1. [立即]  隔离：断开受影响服务的外部网络连接
   iptables -A OUTPUT -d <可疑IP> -j DROP
2. [15min] 取证：保留所有访问日志（audit_log、nginx access log、PG 日志）
3. [30min] 排查：确定泄露范围（哪些用户/哪些数据/泄露途径）
4. [2h]   通知：向风控负责人报告；如涉及个人信息，准备通报监管
5. [4h]   修复：修补漏洞（代码修复/配置加固/权限收缩）
6. [24h]  审计：全量审计日志审查，确认无其他泄露
7. [事后] 改进：更新安全策略，加强访问控制

注意: 不要删除任何日志或数据，保留完整证据链
```

**SOP-03: 数据库主库损坏**

```
现象: PostgreSQL 无法启动或数据文件损坏，无法恢复
影响: 所有读写操作不可用

P1 K8s 生产处理步骤:
1. [5min]  确认 Patroni 状态、PgBouncer 路由和 replica 延迟，禁止直接执行破坏性 `pg_resetwal`
2. [15min] 由 Patroni 提升健康 Replica 为 Primary，PgBouncer write pool 切换到新主库
3. [15min] 验证：核心 API 健康检查 + 10 个冒烟测试 + 写入/读取一致性检查
4. [2h]   如整个 PG 集群不可用，使用 pgBackRest + WAL 归档执行 PITR 恢复
5. [事后] 修复旧主库，按新副本方式重新加入 Patroni 集群

D0 Docker Compose 本地/测试处理步骤:
1. [10min] 确认主库无法恢复后，停止写入并保留现场日志
2. [30min] 如有备份主机，提升备份库或切换 DB_HOST；否则从最近定时备份恢复
3. [30min] 验证核心 API 和登录/案件查询/写入

恢复目标:
- P1 主库故障: RPO < 5min / RTO < 15min
- P1 数据库集群全故障: RPO < 1min / RTO < 2h
- D0 本地/测试环境不承诺生产 RPO/RTO；每日备份场景下恢复演练参考值为 RPO < 24h / RTO < 2h
```

**SOP-04: Elasticsearch 不可用**

```
现象: ES 查询返回错误或超时，搜索功能不可用
影响: 全文检索不可用，知识库检索仅能用向量检索

处理步骤:
1. [5min]  确认：检查 ES 容器状态和日志
   docker compose logs elasticsearch --tail 100
2. [10min] 尝试恢复：
   docker compose restart elasticsearch
3. [15min] 如无法恢复，启用降级：
   - 应用自动检测 ES 不可用 → 跳过全文检索
   - 知识库检索降级为纯向量检索 (PGVector)
   - 审计日志搜索降级为 PG 查询（速度慢但可用）
4. [恢复]  ES 恢复后，重新启用全文检索
5. [事后] 如频繁发生，升级为单节点集群（加副本）

降级行为: 搜索功能降级但可用（仅向量检索，缺少关键词匹配）
```

**SOP-05: 主机磁盘空间不足**

```
现象: 磁盘使用 > 85%，Prometheus 告警触发
影响: 可能导致数据库写入失败（磁盘满）

处理步骤:
1. [10min] 紧急释放空间：
   - 清理 Docker 日志: docker system prune -f
   - 清理旧备份: find /opt/hermes/backup/pg/ -mtime +7 -delete
   - 清理 ES 旧快照
2. [30min] 排查原因：
   - du -sh /opt/hermes/data/* | sort -rh | head -10
3. [2h]   如无法释放足够空间：
   - 加速热→温数据迁移（案件关闭 > 30 天立即迁移）
```

### 8.22 模型版本管理策略

#### 8.22.1 涉及的 AI 模型

| 模型 | 用途 | 升级影响 | 风险等级 |
|------|------|----------|----------|
| **Embedding 模型** | 文档/查询向量化 | 向量维度/语义空间变化 → **全量数据需重新向量化** | 🔴 高 |
| **LLM (DeepSeek)** | 推理/生成 | Prompt 行为可能变化 → 输出质量波动 | 🟡 中 |
| **Whisper (ASR)** | 音频转文字 | 转录结果格式可能变化 | 🟢 低 |
| **PaddleOCR** | 图像文字提取 | OCR 结果文本可能不同 | 🟢 低 |
| **CLIP/ViT** | 图像分类 | 分类标签体系可能变化 | 🟢 低 |
| **unstructured.io** | 文档解析 | Chunk 切分策略变化 → 需重新 Chunking | 🟡 中 |
| **IK 分词器** | ES 中文分词 | 词典变化 → 需重建 ES 索引 | 🟡 中 |

#### 8.22.2 Embedding 模型升级流程（最高风险）

```
当前: text-embedding-3-large (1536d) → 未来可能升级为 text-embedding-4 或本地 bge 模型

升级步骤:
1. [准备阶段，1 周]
   ├── 搭建新向量表 (kb_chunks_v2)，使用新模型维度
   ├── 双写机制：新文档同时写入两个向量表
   └── 混合检索适配器：兼容查询新旧两个向量表

2. [迁移阶段，1-2 周]
   ├── Celery 异步任务批量向量化 (100 chunks/批次)
   ├── 后台执行，不影响正常业务
   └── 进度监控：已迁移 / 总量

3. [切换阶段，1 天]
   ├── Staging 环境验证：检索质量对比 + Re-ranking 准确性
   ├── 选择低峰期（周末）切换
   └── 回滚预案：保留旧向量表至少 30 天

4. [清理阶段，30 天后]
   └── 确认检索质量无退化 → 删除旧向量表
```

#### 8.22.3 LLM 版本升级流程

```
DeepSeek 模型升级 (如 deepseek-v4-pro → deepseek-v5):

1. [评估阶段]
   ├── 准备 50 个标准测试 Prompt（覆盖 8 个模块的关键场景）
   ├── 新旧模型分别运行，人工对比输出质量
   └── 关注：输出格式一致性、推理逻辑准确性、中文表达质量

2. [灰度阶段]
   ├── 10% 流量切换到新模型（按 task_id 哈希）
   ├── LangFuse/Prometheus 监控：成功率、延迟、Token 消耗
   └── 持续 3 天无异常 → 扩大灰度

3. [全量切换]
   └── 100% 切换到新模型，旧模型保留为备用

回滚条件: 成功率 < 98% 或 P95 延迟 > 基线 2x 或人工评估质量下降
```

#### 8.22.4 模型版本矩阵

| 模型 | 当前版本 | 锁定策略 | 升级评估周期 |
|------|----------|----------|-------------|
| text-embedding-3-large | 1536d | API 固定版本号 | 每季度评估 |
| DeepSeek | deepseek-v4-pro | API 固定版本号 | 每季度评估 |

#### 8.22.5 AI 治理与发布门禁

| 风险 | 控制措施 | 发布门禁 |
|------|----------|----------|
| Prompt 注入 | 系统提示隔离、用户输入标记、拒绝执行"忽略规则/越权访问/伪造身份"类指令 | 红队用例全通过 |
| RAG 越权 | 检索前强制注入 `client`、密级和字段权限过滤；引用跨租户文档直接阻断 | 越权召回率 = 0 |
| 工具越权 | Tool 权限矩阵按角色、模块、阶段控制；高风险 Tool（SQL、导出、外部推送）需审批或只读沙箱 | 工具调用审计完整 |
| 幻觉/事实性 | 法规、制度、证据和金额必须带来源引用；无法校验时标注"待人工核实" | 黄金评测集法规/证据引用准确率 ≥ 95% |
| 输出质量漂移 | 50 个标准 Prompt 扩展为模块黄金集；比较格式、结论、置信度、引用和人工评分 | 质量下降即阻断灰度 |
| 高风险自动化 | 涉刑、重大金额、机密下载、处罚执行和外部系统写入必须 HITL | 人工复核记录写入 audit_log |

#### 8.23.2 外部依赖容错设计

```
外部调用模式 (每个外部系统独立 Adapter):

    API Layer
        │
        ▼
    Adapter.call(payload)
        │
        ├── [熔断器] CircuitBreaker(max_failures=5, cooldown=60s)
        │   ├── CLOSED → 正常调用
        │   ├── OPEN   → 直接返回降级结果 (5 次失败后)
        │   └── HALF_OPEN → 试探性调用 (60s 后)
        │
        ├── [重试] RetryPolicy(max_retries=3, backoff=exponential, max_delay=30s)
        │   └── 仅对幂等操作重试 (GET 查询 / 消息投递)
        │
        ├── [超时] Timeout(total=30s, connect=5s)
        │
        └── [降级] Fallback
            ├── 查询类: 返回缓存数据 + stale 标记
            ├── 写入类: 本地队列缓冲，外部恢复后补推
            └── LLM 类: 切换备用模型
```

### 8.24 本地/测试 Docker Compose 方案

> **适用场景**：本地开发、测试环境、PoC、演示和容量验证。该方案不作为正式生产部署方案；生产部署以 P1 K8s 高可用架构为准。如需更详细的部署指导，请参阅 `doc/deployment-plan-100users.md`。

#### 8.24.1 与原架构的差异对照

| 组件 | P1 生产架构 (10K 注册用户) | D0 本地/测试方案 (100 用户测试规模) | 原因 |
|------|-------------------|---------------------|------|
| Kubernetes | 3M + 5W + 2GPU 集群 | ❌ Docker Compose 单机 | 本地/测试无需容器编排 |
| PostgreSQL | Primary + 2 Replicas + PgBouncer | 单实例 + 冷备流复制 | 读写分离对 100 人无意义 |
| Redis | 3 主 3 从 Cluster | 单实例 + AOF | 单实例轻松满足缓存需求 |
| Elasticsearch | 3 节点集群 | 单节点 + 每日快照 | 单节点可处理 5TB 检索 |
| RabbitMQ | 3 节点 quorum queues | 单节点 + 消息持久化 | 消息量极小 |
| MinIO | 4 节点 EC 12+4 | 单节点 + RAID1 | 数据通过 rsync 备份 |
| Nginx | 2 节点 + Keepalived | 单节点 + Docker restart | Nginx 挂了 Docker 自重启 |
| Jaeger | 分布式追踪 | ❌ structlog traceId | 3-5 个服务无需分布式追踪 |
| LangFuse | LLM 可观测 | ❌ Prometheus + structlog | LLM 调用量小 (日 < 1000 次) |
| Harbor | 内网镜像仓库 | ❌ Docker Hub / GHCR | 镜像量小 |
| PgBouncer | 连接池 | ❌ PG 原生连接 | 连接数 < 30 |
| GPU Worker | 2× V100 32G | ⏸️ 延期 (可后补 1× A4000) | 第一版仅 CPU 文档解析 |
