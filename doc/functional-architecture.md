### 1.2 端到端请求处理流程

一次典型的 AI 功能调用，从用户操作到返回结果的全链路：

```
用户请求 (如：创建案件)
  │
  ├─ 1. API 网关接收 (Nginx SSL 终结, 限流检查)
  │    └─ JWT 验证 → RBAC 权限过滤 → 生成 traceId
  │
  ├─ 2. 意图识别与路由
  │    └─ 解析请求类型 → 匹配工作流模块 → 创建/恢复 LangGraph 线程
  │
  ├─ 3. 上下文组装 (ContextEngineering)
  │    ├─ 加载 System Prompt 模板 (PromptManager)
  │    ├─ 注入阶段知识 (RAG 检索)
  │    ├─ 加载历史摘要 (L2 会话记忆)
  │    ├─ 注入案例上下文 (L3 案例记忆)
  │    └─ 组装完整的 LLM 输入上下文
  │
  ├─ 4. LLM 推理 (Agent 核心)
  │    ├─ Token 预算检查 → 裁剪/压缩 (如超限)
  │    ├─ LLM Adapter 调用 (DeepSeek 主 → 失败则通义千问备)
  │    ├─ Tool Calling: LLM 决策调用哪些工具
  │    │   ├─ kb_search → RAG 检索知识库
  │    │   ├─ sql_execute → 执行业务数据查询
  │    │   ├─ es_search → 全文检索历史文档
  │    │   └─ 其他工具...
  │    └─ 多轮 ReAct 循环: 思考 → 行动 → 观察 → 思考...
  │
  ├─ 5. 结果处理
  │    ├─ 结构化输出解析 (Pydantic Schema 校验)
  │    ├─ 文档生成 (docx/xlsx 异步生成)
  │    ├─ 状态持久化 (Checkpointer → Redis)
  │    └─ 审计日志记录 (不可篡改)
  │
  ├─ 6. HITL 守门 (如需人工确认)
  │    ├─ interrupt_before 挂起工作流
  │    ├─ WebSocket 推送守门任务 → 用户审核
  │    └─ 用户确认/修改/驳回 → resume 继续
  │
  └─ 7. 响应返回
       ├─ 同步: API Response (task_id + 当前状态)
       ├─ 异步: WebSocket 推送进度更新
       └─ 外部同步: A2A/风控系统状态回写
```

## 二、意图识别

### 2.1 什么是意图识别

意图识别是赫尔墨斯理解"用户想要什么"的入口功能。不同于传统聊天机器人的 NLU 意图分类，赫尔墨斯的意图识别是**结构化路由决策**——用户通过明确的业务操作（按钮点击、表单提交）触发，系统通过上下文感知决定执行哪个工作流阶段。

### 2.2 意图识别层次

赫尔墨斯的意图识别分为三个层次：

```
┌─────────────────────────────────────────────────────────────────┐
│                     意图识别三层模型                               │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L1: 操作意图 (Operation Intent)                              │ │
│  │  识别方式: API 路由 + 操作码                                   │ │
│  │  示例: POST /api/v1/cases/{id}/workflow/start                │ │
│  │        → 意图 = "启动廉洁监察工作流"                            │ │
│  │  准确率: 100% (确定性路由)                                     │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↓                                    │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L2: 阶段意图 (Stage Intent)                                  │ │
│  │  识别方式: LangGraph 状态机 + 上下文决策                        │ │
│  │  示例: 材料初判完成后 → 意图 = "继续调查" | "转交HR" | "不处理"  │ │
│  │  准确率: AI 辅助决策 + 碳基守门确认                             │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↓                                    │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L3: 工具意图 (Tool Intent)                                   │ │
│  │  识别方式: LLM Function Calling                               │ │
│  │  示例: "需要检索历史类似案件" → kb_search 工具调用              │ │
│  │  准确率: 取决于 LLM 推理能力和 Tool Description 质量            │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 意图识别实现流程

#### L1 操作意图（确定性路由）

```python
# 操作意图通过 API 路由直接确定，无需 AI 推理
class CaseWorkflowRouter:
    """案件工作流路由 - 确定性意图识别"""

    OPERATION_MAP = {
        "workflow/start": "启动工作流",
        "workflow/resume": "恢复工作流 (守门确认后)",
        "approval/intake": "材料初判守门审批",
        "approval/investigation": "调查方案守门审批",
        "approval/analysis": "分析报告守门审批",
        "approval/disposition": "处置分流守门审批",
        "approval/enforcement": "处罚执行守门审批",
    }

    def resolve_intent(self, request: Request) -> Intent:
        # 1. 从 URL 路径和 HTTP Method 确定操作意图
        operation = self.OPERATION_MAP.get(request.path_pattern)

        # 2. 加载当前工作流状态 (如有)
        state = self.load_workflow_state(request.case_id)

        # 3. 验证操作合法性
        if state and not self.is_valid_transition(state, operation):
            raise InvalidIntentError(f"当前状态 {state.current_stage} 不允许执行 {operation}")

        return Intent(
            type="operation",
            module=state.module,
            stage=state.current_stage,
            operation=operation
        )
```

#### L2 阶段意图（AI 辅助决策 + 条件路由）

```python
# LangGraph 条件路由 - AI 根据上下文决定分流路径
def route_after_intake(state: HermesState) -> str:
    """
    材料初判后的分流决策。
    虽然 LLM 已经输出了分流建议，但最终路由逻辑是确定性的，
    基于 LLM 输出的结构化字段 + 碳基守门结果。
    """
    if not state.should_investigate:
        return "close_case_not_handled"  # → 闭环

    if state.should_transfer:
        if state.is_hr_related:
            return "transfer_to_hr"       # → A2A 龟宝
        else:
            return "transfer_to_other"    # → 任务中心转交

    return "continue_investigation"       # → 继续调查

# StateGraph 中注册条件路由
graph.add_conditional_edges(
    "intake_node",
    route_after_intake,
    {
        "close_case_not_handled": "close_case_node",
        "transfer_to_hr": "a2a_transfer_node",
        "transfer_to_other": "task_center_node",
        "continue_investigation": "investigation_node",
    }
)
```

#### L3 工具意图（LLM Function Calling）

```
LLM 工具意图识别的 Prompt 设计:

【可用工具说明】
你拥有以下工具可以调用。当需要获取信息或执行操作时，选择合适的工具：

1. kb_search_risk_rules: 检索历史风险规则、数据库字段定义、相似案例
   使用时机：需要参考历史数据、法规制度、类似案例时
   参数：query (搜索关键词), kb_type (知识库类型), top_k (返回条数)

2. sql_batch_execute: 执行业务数据库 SQL 查询
   使用时机：需要获取业务数据进行分析时
   参数：sql (SQL 语句), timeout (超时时间)

3. external_data_query: 查询外部数据（企查查、舆情等）
   使用时机：需要工商信息、外部风险数据时
   参数：query_type (查询类型), query_params (查询参数)

4. push_risk_result: 推送风险结果到目标模块
   使用时机：风险定性完成后需要通知下游模块时
   参数：target_module (目标模块), risk_data (风险数据)

【工具选择规则】
- 优先使用知识库检索获取上下文，再进行数据查询
- SQL 查询前必须先用 EXPLAIN 验证
- 外部数据作为补充，不影响主流程
```

## 三、记忆系统

### 3.1 设计理念

记忆是 AI 智能体区别于传统规则系统的核心能力。赫尔墨斯采用**分层记忆架构**，实现从瞬时感知到持久知识的完整记忆谱系。四层记忆遵循"**从短到长，逐层固化**"的原则：

- **越上层越具体**（单次调用上下文）
- **越下层越抽象**（跨案件知识模式）
- **信息单向流动**：L1 → L2 → L3 → L4
- **每层都有自己的存储、检索策略和生命周期**

### 3.2 四层记忆架构

```
┌─────────────────────────────────────────────────────────────────┐
│                    赫尔墨斯记忆分层架构                             │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L4: 组织记忆 (Organizational Memory)   持久性: 永久           │ │
│  │  ─────────────────────────────────────────────────────────  │ │
│  │  内容: 制度法规 | 历史案例库 | 审计报告模板 | 风险规则库         │ │
│  │       处置经验 | 缺陷模式 | 访谈问题库 | 定密评审记录           │ │
│  │  存储: PGVector (向量) + Elasticsearch (全文) + PostgreSQL    │ │
│  │  更新: 案件闭环自动入库 + 人工审核 + 定期清理过时内容           │ │
│  │  检索: 混合检索 (语义+关键词+结构化过滤) + Re-ranking          │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 固化 (案件闭环后自动/人工入库)        │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L3: 案例记忆 (Episodic Memory)         持久性: 案件全生命周期  │ │
│  │  ─────────────────────────────────────────────────────────  │ │
│  │  内容: 案件工作流状态 | 各阶段 AI 产出物 | 碳基守门决策记录       │ │
│  │        A2A 交互记录 | 证据材料索引 | 外部同步状态               │ │
│  │  存储: Redis (活跃 Checkpointer) + PostgreSQL (持久化)         │ │
│  │  检索: SQL 结构化查询 (同类型/同部门/同金额) + PGVector 相似案例 │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 聚合 (阶段完成，守门通过后写入)       │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L2: 会话记忆 (Conversational Memory)    持久性: 单阶段周期     │ │
│  │  ─────────────────────────────────────────────────────────  │ │
│  │  内容: LLM 对话历史 (messages[]) | 本轮 RAG 召回片段             │ │
│  │        Tool 调用结果缓存 | 上下文压缩摘要                       │ │
│  │  存储: Redis (热数据) + LangGraph State (序列化)                │ │
│  │  管理: 滑动窗口 + 自动摘要压缩 + 分层注入                        │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                              ↑ 交互 (每次 LLM 调用累积)            │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  L1: 感知记忆 (Sensory Memory)          持久性: 瞬时 (单次调用)  │ │
│  │  ─────────────────────────────────────────────────────────  │ │
│  │  内容: 用户输入 | 多模态感知结果 (ASR转录/OCR文本)               │ │
│  │        System Prompt | 阶段知识注入 | 历史摘要                  │ │
│  │  存储: LLM Context Window (GPU 显存, 调用结束释放)              │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 记忆流转详解

#### 3.3.1 L1 → L2：从瞬时感知到对话上下文

```
每次 LLM 调用的信息流:

用户输入 + System Prompt + RAG 召回结果
         │
         ▼
    ┌─────────────────┐
    │  L1 感知记忆组装  │  ← ContextEngineering 负责构建
    │  (Context Window) │
    └────────┬────────┘
             │
             ▼
    ┌─────────────────┐
    │    LLM 推理       │  ← DeepSeek/通义千问
    └────────┬────────┘
             │
             ▼
    LLM 输出 (文本 + Tool Calls) → 追加到 state.messages
             │
             ▼
    ┌─────────────────┐
    │  L2 会话记忆更新  │  ← 累积的对话历史
    │  state.messages  │     超长时触发压缩 (摘要)
    └─────────────────┘
```

```
工作流阶段完成 + 碳基守门通过:

    ┌─────────────────┐
    │  L2 会话记忆      │
    │  (阶段对话+产出)  │
    └────────┬────────┘
             │
             ▼
    ┌─────────────────────┐
    │  信息提取与结构化     │
    │  - 关键事实           │
    │  - 决策逻辑           │
    │  - AI 产出物 (报告等) │
    │  - 碳基修改记录       │
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │  L3 案例记忆写入      │
    │  - PG: cases 表更新   │
    │  - PG: stage_outputs  │
    │  - Redis: Checkpointer│
    └─────────────────────┘
```

#### 3.3.3 L3 → L4：从单一案例到组织知识

```
案件闭环触发固化流程:

    ┌─────────────────┐
    │  L3 案例记忆      │
    │  (完整案件档案)   │
    └────────┬────────┘
             │
             ▼
    ┌─────────────────────────────┐
    │  知识抽取 (AI + 结构化规则)  │
    │                             │
    │  调查报告 → 案例库           │
    │  处置经验 → 规则库           │
    │  缺陷模式 → 指标库           │
    │  访谈策略 → 访谈问题库       │
    │  法律论证 → 法务知识库       │
    └────────┬────────────────────┘
             │
             ▼
    ┌─────────────────────────────┐
    │  L4 组织记忆更新             │
    │                             │
    │  自动入库 (普通案件)         │
    │  人工审核 (高风险/涉刑案件)   │
    │  Embedding + ES 索引         │
    │  版本标记 + 时效性标记       │
    └─────────────────────────────┘
```

### 3.4 跨案件学习闭环

```
案件 A 完成 ──→ 处置经验 → 规则库更新
                              │
                              ▼
案件 B 启动 ──→ RAG 检索 ──→ 命中案件 A 的经验
                              │
                              ▼
                   调查方案自动引用先例
                   风险定性更准确 (有参照)
                   处置建议更合理 (有判例)
                              │
                              ▼
案件 B 完成 ──→ 新经验补充 ──→ 规则库再次更新
                              │
                   持续迭代, 准确率不断上升
```

**固化机制的关键规则**：
- **衰减机制**：过时案例（如法律法规已变更）标记为"仅供参考"，检索权重降低 70%
- **验证机制**：高风险案件（涉及刑事/重大金额 ≤ 50万）需人工审核后入库
- **去重机制**：同一模式的多个案例合并为一个模式条目 + 多实例引用

## 四、RAG 召回系统

### 4.1 RAG 在赫尔墨斯中的定位

RAG（Retrieval-Augmented Generation，检索增强生成）是赫尔墨斯实现"知识驱动决策"的核心引擎。每个工作流阶段启动时，系统从知识库中检索最相关的上下文注入到 LLM Prompt，而非仅依赖 LLM 参数记忆。

### 4.2 RAG 检索架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                         RAG 引擎架构                                  │
│                                                                      │
│  用户查询 / 阶段上下文                                                │
│       │                                                              │
│       ▼                                                              │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                    查询预处理 (Query Preprocessing)             │    │
│  │  ├── 查询意图分类 (语义搜索 vs 精确匹配)                         │    │
│  │  ├── 查询扩展 (同义词/相关词自动扩展)                            │    │
│  │  ├── 租户过滤注入 (client = ecovacs/tineco/group)              │    │
│  │  ├── 密级过滤注入 (仅返回用户有权访问的文档)                     │    │
│  │  └── 时效性过滤 (排除已废止的法规/过时的案例)                    │    │
│  └─────────────────────────────────────────────────────────────┘    │
│       │                                                              │
│       ▼                                                              │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                    混合检索 (Hybrid Search)                     │    │
│  │                                                                  │    │
│  │  ┌─────────────────────┐    ┌─────────────────────────────┐    │    │
│  │  │  向量语义检索         │    │  全文关键词检索               │    │    │
│  │  │  (PGVector + HNSW)   │    │  (Elasticsearch + BM25)     │    │    │
│  │  │                     │    │                             │    │    │
│  │  │  索引: HNSW 图索引   │    │  索引: 倒排索引 + IK分词     │    │    │
│  │  │  距离: cosine        │    │  算法: BM25 相关性评分      │    │    │
│  │  │  维度: 1536d         │    │  分词: ik_max_word         │    │    │
│  │  │  召回: Top 20        │    │  召回: Top 20              │    │    │
│  │  └──────────┬──────────┘    └──────────────┬──────────────┘    │    │
│  │             └────────────┬─────────────────┘                    │    │
│  │                          ▼                                      │    │
│  │  ┌─────────────────────────────────────────────────────────┐    │    │
│  │  │              结果融合 (Reciprocal Rank Fusion)             │    │    │
│  │  │  RRF_score = Σ 1/(k + rank_i)                            │    │    │
│  │  │  向量检索权重: 0.7 | 全文检索权重: 0.3 (可配置)           │    │    │
│  │  └─────────────────────────────────────────────────────────┘    │    │
│  └─────────────────────────────────────────────────────────────┘    │
│       │                                                              │
│       ▼                                                              │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                    Re-ranking (重排序)                          │    │
│  │  ├── Cross-Encoder 模型精排 (或 LLM-based 重排序)               │    │
│  │  ├── 多样性优化 (MMR 算法, 避免相似文档堆叠)                    │    │
│  │  └── 最终返回: Top 5 最相关 + 多样化文档片段                    │    │
│  └─────────────────────────────────────────────────────────────┘    │
│       │                                                              │
│       ▼                                                              │
│  注入 LLM Context Window (作为 System Prompt 的知识注入部分)         │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.3 多分区知识库索引

赫尔墨斯为每个业务阶段维护独立的知识库分区，实现精确的知识隔离：

| 知识库分区 | 内容 | 存储 | 检索维度 | 使用模块 |
|-----------|------|------|----------|----------|

### 4.4 RAG 检索触发时机

每个 Agent 在每个工作流阶段都会触发 RAG 检索：

```
工作流节点启动
    │
    ├── 1. 加载节点配置 (包含 kb_types 列表)
    │
    ├── 2. 构建检索查询
    │   ├── 自动查询: 从 state 中提取关键字段 (案件类型/部门/金额区间)
    │   └── LLM 生成查询: LLM 根据当前上下文动态生成最佳检索查询
    │
    ├── 3. 执行多路检索 (并行)
    │   ├── PGVector 语义检索 (cosine similarity, Top 20)
    │   └── Elasticsearch 全文检索 (BM25, Top 20)
    │
    ├── 4. 结果融合 (RRF) + Re-ranking (Top 5)
    │
    ├── 5. 注入 System Prompt
    │   └── "【知识注入】以下是知识库中与当前任务最相关的参考信息：..."
    │
    └── 6. LLM 推理 (携带知识上下文)
```

### 4.5 RAG 性能指标

| 指标 | 目标 | 实现方式 |
|------|------|----------|
| 检索延迟 P95 | < 200ms | PGVector HNSW 索引 + ES 分布式检索 并行执行 |
| 检索覆盖率 | > 80% 查询返回相关结果 | 混合检索 (语义+关键词) + 查询扩展 |
| 检索准确率 (Top 5) | > 70% 结果相关 | Re-ranking + 用户反馈闭环 |
| 向量维度 | 1536d (text-embedding-3-large) | 兼容 OpenAI Embedding 接口 |

### 5.3 Prompt 模板结构

每个 Agent 的 Prompt 模板遵循统一的六段式结构：

```yaml
# prompts/integrity/intake-agent.yaml
version: "2.3.0"
agent_id: "intake-agent"
description: "廉洁监察初筛 Agent - 材料初判与分流决策"
last_updated: "2026-06-01"

system_prompt:
  # === 段一: 角色锚定 (Role Anchoring) ===
  role_anchoring: |
    你是一位拥有15年反舞弊调查经验的资深案件初审官。
    你曾在大型企业集团的监察部门工作，处理过上百起各类舞弊案件。
    你的核心能力是：快速识别案件性质、评估可查性、做出精准的分流决策。

  # === 段二: 核心任务 (Core Task) ===
  core_task: |
    根据提交的案件材料，完成以下任务：
    1. 分析案件核心事实和涉及的主要风险点
    2. 评估案件的可查性（是否有调查价值、是否有足够线索）
    3. 做出分流决策：不处理 / 转交其他部门 / 继续调查
    4. 给出详细的分析理由和建议处置方式

  # === 段三: 工作规范 (Working Standards) ===
  working_standards: |
    - 不处理案件必须明确说明不处理的具体原因
    - 转交案件必须指明转交的目标部门或Agent
    - 继续调查案件必须列出初步的调查方向

  # === 段四: 输出格式约束 (Output Format) ===
  output_format: |
    你必须严格按照以下JSON格式输出：
    {
      "should_investigate": true/false,
      "should_transfer": true/false/null,
      "transfer_target": "hr/legal/other/null",
      "is_hr_related": true/false,
      "analysis_reason": "详细分析理由",
      "preliminary_direction": "初步调查方向建议",
      "risk_level": "高/中/低",
      "confidence": "high/medium/low"
    }

  # === 段五: 安全底线 (Safety Constraints) ===
  safety_constraints: |
    - 禁止在没有充分信息的情况下做出确定性结论
    - 涉及刑事犯罪的案件必须标记"建议移送司法程序"
    - 所有判断必须基于案件材料提供的客观事实
    - 不得对案件涉及的个人进行人身攻击或道德审判

  # === 段六: Few-shot 示例 (Few-shot Examples) ===
  few_shot_examples: |
    示例1: [采购舞弊案] → should_investigate=true, risk_level=高, ...
    示例2: [轻微违规案] → should_transfer=true, transfer_target=hr, ...
    示例3: [信息不足案] → should_investigate=false, ...
```

### 5.4 Prompt 变量注入机制

运行时通过 Jinja2 模板引擎将动态变量注入 Prompt：

```python
class PromptManager:
    """提示词管理器 - 负责加载、渲染、版本控制"""

    def render_prompt(
        self,
        agent_id: str,
        variables: dict
    ) -> PromptRenderResult:
        """
        渲染 Agent 的 System Prompt。
        注入的变量包括:
        - DB_SCHEMA: 数据库字段及含义（知识库检索结果）
        - HISTORICAL_CASES: 历史相似案例
        - CURRENT_CASE: 当前案件结构化信息
        - REGULATIONS: 相关法规制度
        - RISK_CRITERIA: 风险等级判定标准
        - PERSONNEL_DUTIES: 相关人员岗位职责
        """
        template = self.load_template(agent_id)

        # 1. 渲染模板
        system_prompt = template.render(**variables)

        # 2. Token 预算检查
        token_count = self.count_tokens(system_prompt)
        if token_count > template.token_budget:
            logger.warning(
                f"Prompt token overflow: {agent_id} "
                f"used {token_count}/{template.token_budget}"
            )
            # 触发裁剪策略 (见上下文工程)

        # 3. 上报 LangFuse
        self.track_prompt_version(agent_id, template.version, token_count)

        return PromptRenderResult(
            system_prompt=system_prompt,
            token_count=token_count,
            version=template.version,
        )
```

### 5.5 Prompt 版本管理策略

| 维度 | 策略 |
|------|------|
| **版本格式** | `主版本.次版本.修订号` (如 `2.3.0`) |
| **变更追踪** | 每次修改在 Git 中提交，在 LangFuse 中追踪实际使用版本 |
| **灰度发布** | 新 Prompt 先在 10% 流量验证 3 天 → 人工评估质量 → 全量 |
| **回滚机制** | 保留最近 5 个版本，一键回滚 |
| **A/B 测试** | 支持按 task_id 哈希分流，对比新旧 Prompt 的质量指标 |

### 5.6 Token 预算管理

每个 Agent 的 System Prompt 有明确的 Token 预算：

| 组成部分 | 典型预算 | 说明 |
|----------|---------|------|
| 角色锚定 | ~1,200 tokens | 固定部分，极少变更 |
| Few-shot 示例 | ~1,500 tokens | 示例数量按需调整 |
| 知识注入 (RAG) | ~4,000 tokens | 动态变化，超限时压缩 |
| 工作规范 | ~500 tokens | 固定部分 |
| 输出约束 | ~300 tokens | JSON Schema 描述 |
| 安全底线 | ~300 tokens | 固定部分 |
| **System Prompt 小计** | **~7,800 tokens** | |
| 对话历史 (L2) | ~4,000 tokens | 超长时自动摘要 |
| 用户输入 | ~3,000 tokens | 含附件文本 |
| 输出预留 | ~4,000 tokens | LLM 回复空间 |
| **总计预算** | **~18,800 tokens** | **远低于 64K 上限** |

## 六、上下文工程

### 6.1 什么是上下文工程

上下文工程（Context Engineering）是赫尔墨斯中最核心的功能编排能力——它决定了**每次 LLM 调用时，模型"看到"什么信息**。上下文工程不是简单的字符串拼接，而是一个有策略的、分层的、动态的组装过程。

### 6.2 上下文组装流程

```
每次 LLM 调用前的上下文构建流水线:

┌─────────────────────────────────────────────────────────────────────┐
│                     Context Builder (上下文构建器)                      │
│                                                                      │
│  Step 1: 加载基础模板                                                 │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  System Prompt 模板 (PromptManager)                            │   │
│  │  ↓ 固定内容: 角色锚定 + 工作规范 + 输出格式 + 安全底线            │   │
│  │  ↓ 动态内容: Few-shot 示例 (按阶段选择)                          │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 2: 注入知识 (RAG 检索结果)                                      │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  【知识注入】标签包裹                                            │   │
│  │  ├── 相关制度法规 (从 kb_common 检索, Top 3)                     │   │
│  │  ├── 历史相似案例 (从 kb_intake 检索, Top 3)                     │   │
│  │  ├── 数据库字段定义 (从 kb_risk_rules 检索)                      │   │
│  │  └── 组织架构信息 (从 kb_common 结构化查询)                      │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 3: 注入案例上下文 (L3 案例记忆)                                  │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  【案件上下文】标签包裹                                          │   │
│  │  ├── 当前案件基本信息 (case_id, 涉案主体, 涉案金额, 事业部)       │   │
│  │  ├── 前序阶段产出摘要 (初判报告摘要 → 调查方案引用)              │   │
│  │  └── 碳基修改记录摘要 (守门时做了哪些调整)                       │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 4: 注入历史摘要 (L2 会话记忆)                                    │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  【历史对话摘要】标签包裹 (仅当本阶段有 > 5 轮对话时)              │   │
│  │  └── LLM 生成的 200 token 结构化摘要                             │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 5: 注入用户输入                                                 │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  【用户输入】                                                    │   │
│  │  ├── 结构化表单数据 (字段名+值)                                   │   │
│  │  ├── 附件引用 (文件名 + RAG 检索到的相关片段)                     │   │
│  │  └── 用户备注/指令                                               │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 6: Token 预算检查与裁剪                                         │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  if total_tokens > budget:                                     │   │
│  │    1. 压缩 RAG 结果 (Top 5 → Top 3, 截断过长片段)               │   │
│  │    2. 压缩历史摘要 (200 token → 100 token)                      │   │
│  │    3. 启动滑动窗口 (仅保留最近 16K tokens 对话)                  │   │
│  │    4. 如仍超限 → 拒绝请求, 告警, 建议分批处理                    │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  Step 7: 最终组装                                                    │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  messages = [                                                   │   │
│  │    SystemMessage(system_prompt),                                │   │
│  │    *state.messages[-N:],  ← L2 对话历史                         │   │
│  │    HumanMessage(user_input),                                    │   │
│  │  ]                                                              │   │
│  └──────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
```

### 6.4 上下文工程的实现代码

```python
class ContextBuilder:
    """上下文构建器 - 负责组装每次 LLM 调用的完整上下文"""

    def __init__(
        self,
        prompt_manager: PromptManager,
        rag_engine: RAGEngine,
        memory_store: MemoryStore,
    ):
        self.prompt_manager = prompt_manager
        self.rag_engine = rag_engine
        self.memory_store = memory_store

    async def build(
        self,
        agent_id: str,
        state: HermesState,
        user_input: str,
        token_budget: int = 20000,
    ) -> list[BaseMessage]:
        """构建完整的 LLM 输入消息列表"""

        # Step 1: 加载 Agent 的 System Prompt 模板
        template = self.prompt_manager.load_template(agent_id)

        # Step 2: 执行 RAG 检索 (并行多路)
        kb_context = await self._build_knowledge_context(
            agent_id=agent_id,
            state=state,
        )

        # Step 3: 加载 L3 案例记忆
        case_context = await self._build_case_context(state)

        # Step 4: 管理 L2 会话记忆
        conversation_context = await self._build_conversation_context(
            state, token_budget
        )

        # Step 5: 渲染 System Prompt
        system_prompt = template.render(
            db_schema=kb_context.get("db_schema", ""),
            historical_cases=kb_context.get("cases", []),
            regulations=kb_context.get("regulations", []),
            case_summary=case_context,
            previous_stage_summary=conversation_context.get("summary", ""),
        )

        # Step 6: Token 预算检查与裁剪
        system_prompt = self._trim_to_budget(
            system_prompt, state.messages, user_input, token_budget
        )

        # Step 7: 组装最终消息列表
        messages = [
            SystemMessage(content=system_prompt),
            *self._apply_sliding_window(state.messages, token_budget),
            HumanMessage(content=user_input),
        ]

        return messages

    async def _build_knowledge_context(
        self, agent_id: str, state: HermesState
    ) -> dict:
        """构建知识库上下文（并行检索多个知识库分区）"""
        kb_types = self._get_kb_types_for_agent(agent_id)

        # 并行检索
        results = await asyncio.gather(*[
            self.rag_engine.hybrid_search(
                query=self._build_search_query(state, kb_type),
                kb_type=kb_type,
                top_k=5,
            )
            for kb_type in kb_types
        ])

        return self._format_kb_results(results, kb_types)

    def _trim_to_budget(
        self,
        system_prompt: str,
        history: list,
        user_input: str,
        budget: int,
    ) -> str:
        """Token 预算裁剪"""
        current_tokens = (
            self._count_tokens(system_prompt) +
            self._count_tokens(history) +
            self._count_tokens(user_input) +
            4000  # 输出预留
        )

        if current_tokens <= budget:
            return system_prompt

        # 裁剪优先级: RAG结果 → Few-shot → 历史摘要
        # (逐步压缩，每次压缩后重新计算)
        ...
```

## 七、工作流编排引擎

### 7.1 为什么需要工作流引擎

赫尔墨斯的每个业务模块都包含多个阶段的复杂工作流：

- 廉洁监察：6 阶段，含 4 个条件分支
- 风险监控：6 阶段，含 3 个子阶段流水线
- 内控评价：13 步骤，含并行和串行混合
- 持续改善：5 状态流转，含退回重审循环

LangGraph 被选为工作流引擎，因为它在 LLM Agent 工作流场景中有原生优势。

### 7.3 工作流执行时序

```
用户触发: POST /api/v1/cases/{id}/workflow/start

    │
    ▼
1. WorkflowService 创建 thread_id = case_id
    │
    ▼
2. graph.ainvoke(initial_state, config={"configurable": {"thread_id": ...}})
    │
    ▼
3. [intake_node] 执行
    ├── Context Builder 组装上下文
    ├── RAG 检索知识库
    ├── LLM 推理 → 生成初判报告
    ├── State 更新: intake_report = {...}
    ├── Checkpointer 自动保存
    └── 无 interrupt → 继续下一节点
    │
    ▼
4. [route_after_intake] 条件判断
    ├── state.should_investigate == false → close_case (END)
    ├── state.should_transfer == true → a2a_transfer (END)
    └── else → investigation_node
    │
    ▼
5. [investigation_node] 执行 ← interrupt_before 触发
    ├── 工作流挂起, 状态设为 "pending_approval"
    ├── WebSocket 推送 → 用户收到待审核通知
    └── 等待用户操作...
    │
    ▼
6. 用户审核并确认 (POST /api/v1/cases/{id}/approval/investigation)
    ├── approval_result = "approved"
    └── POST /api/v1/cases/{id}/workflow/resume
    │
    ▼
7. 工作流恢复 → investigation_node 继续 → 执行 agent 逻辑
    ├── State 更新 → Checkpointer 保存
    └── → [analysis_node] → [disposition_node] → ...
    │
    ▼
8. 最终节点 → END → 闭环
    └── 触发后续任务: 数据迁移计时器、L3→L4 固化排队
```

### 8.2 工具定义规范

```python
@tool(
    tool_id="kb_search_risk_rules",
    name="知识库检索-风险规则",
    description="检索历史风险规则、数据库字段定义、历史案例。"
                "使用时机：需要参考历史数据、法规制度、类似案例时。",
    permissions=["kb:read"],
    timeout=5,  # 秒
    retry=RetryPolicy(max_retries=1, backoff="exponential"),
)
async def kb_search_risk_rules(
    query: str = Field(description="搜索关键词或自然语言查询"),
    kb_type: str = Field(
        default="risk_rules",
        description="知识库类型: risk_rules | risk_history | regulations"
    ),
    top_k: int = Field(default=5, ge=1, le=20, description="返回结果数量"),
    filters: dict | None = Field(
        default=None,
        description="结构化过滤条件，如 {\"business_cycle\": \"采购\"}"
    ),
) -> ToolResult:
    """
    工具实现: RAG 混合检索
    """
    # 1. 权限检查
    verify_permission("kb:read", kb_type)

    # 2. 租户过滤注入
    filters = filters or {}
    filters["client"] = current_user.client

    # 3. 执行混合检索
    results = await rag_engine.hybrid_search(
        query=query,
        kb_type=kb_type,
        top_k=top_k,
        filters=filters,
    )

    # 4. 返回结构化结果（含文档来源引用）
    return ToolResult(
        success=True,
        data={
            "results": [
                {
                    "content": r.content,
                    "source": r.source,
                    "relevance": r.score,
                    "doc_id": r.doc_id,
                }
                for r in results
            ],
            "total_found": len(results),
        }
    )
```

### 10.3 多模态处理与 Agent 工作流的集成

多模态处理通过**引用而非内嵌**的方式与 Agent 工作流集成：

```python
# Agent 中的多模态数据使用模式
class MultiModalContextProvider:
    """为 Agent 提供多模态处理结果的上下文"""

    async def get_transcript_context(
        self, file_id: str, query: str | None = None
    ) -> str:
        """获取音频转录的上下文"""
        # 1. 从 ES 中检索转录全文 (关键词匹配)
        transcript = await es.get(
            index="hermes-transcripts",
            id=file_id,
        )

        # 2. 如果有关注点，用 PGVector 检索最相关的片段
        if query:
            relevant_segments = await pgvector.search(
                kb_type="transcripts",
                query=query,
                filters={"file_id": file_id},
                top_k=5,
            )
            return self._format_segments(relevant_segments)

        # 3. 返回摘要 (前 2000 字 + 说话人统计)
        return self._format_summary(transcript)

    async def get_document_context(
        self, doc_id: str, focus_area: str | None = None
    ) -> str:
        """获取文档的上下文片段（引用模式）"""
        if focus_area:
            # 语义检索最相关的 chunks
            chunks = await rag_engine.hybrid_search(
                query=focus_area,
                kb_type="documents",
                filters={"doc_id": doc_id},
                top_k=10,
            )
            return self._format_chunks(chunks)
        else:
            # 返回文档摘要
            return await self._get_doc_summary(doc_id)
```

## 十一、人机协同 (HITL)

### 11.1 碳基守门设计原则

赫尔墨斯的核心理念是"**AI 辅助决策，人类最终确认**"。每个可能产生重要影响的 AI 输出都需要经过"碳基守门"（Human-in-the-Loop Gate）。

### 11.2 守门机制实现

```
┌─────────────────────────────────────────────────────────────────────┐
│                      HITL 守门工作流                                    │
│                                                                      │
│  工作流引擎编译时配置:                                                 │
│  app = graph.compile(                                                │
│      checkpointer=redis_checkpointer,                                │
│      interrupt_before=[                                              │
│          "investigation_node",   # AI 生成调查方案后暂停             │
│          "analysis_node",        # AI 生成分析报告后暂停             │
│          "disposition_node",     # AI 生成处置意见后暂停             │
│          "enforcement_node",     # AI 生成处罚方案后暂停             │
│      ]                                                               │
│  )                                                                   │
│                                                                      │
│  执行流程:                                                           │
│                                                                      │
│  1. AI 生成阶段输出                                                   │
│     ├── LLM 推理 → 生成报告/方案/意见                                  │
│     ├── State 更新 (如: intake_report = {...})                      │
│     └── Checkpointer 保存状态                                         │
│                                                                      │
│  2. 工作流挂起 (interrupt_before 触发)                                 │
```

### 15.1 LangGraph Checkpointer 机制

赫尔墨斯的工作流状态通过 LangGraph 的 Checkpointer 机制实现持久化：

```python

from langgraph.checkpoint.redis import RedisSaver

# P1 生产: Redis Cluster
redis_checkpointer = RedisSaver(
    redis_client=redis_cluster_client,
    ttl=timedelta(days=7),  # 活跃状态保留 7 天
)

# D0 本地: 备选 SQLite/PostgreSQL Checkpointer
# postgres_checkpointer = PostgresSaver(conn_string)

# 编译工作流时注入
app = graph.compile(
    checkpointer=redis_checkpointer,
    interrupt_before=[...],
)
```
